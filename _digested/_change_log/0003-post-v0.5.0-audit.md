## 二、这轮做了什么

### 2.1 先把校验做成工具，而不是做成一次性的手工核对

`_digested/_tools/check_anchors.py`：把两个文档目录里所有 `文件:行号` 锚点解析到工作树，报两类失效——NOFILE（文件已不存在）与 OOB（文件比引用行号短）。墓碑（指向已删除机制的锚点）按行内标记豁免。

首跑 **688 个锚点 / 3 个真失效**，修完归零（`7b3488d96`）。3 个失效里 1 个是 `integration-evidence` 把 Web Studio 块写成 `app.py:793-833`（旧锚点），而该文件总共 812 行——**引用越过了文件末尾**，纯手工核时看不出来。

它的价值不在于功能复杂，而在于**它让"锚点腐烂"从主观变成可回归**。以后的同步轮第一步就该是它。

### 2.2 抓住那个最贵的错误："某层没变"

"某层没变"是所有断言里最容易写、最难查、破坏力最大的一种：

- 它**不指向任何一行代码**，所以锚点检查器抓不到它；
- 它会**连带作废一整篇的立论前提**；
- 它读起来像谨慎（"我确认过了，没动"），实际是**概括性偷懒**。

本轮抓到两处，同一根源：

| 位置 | 原话 | 实测 |
|---|---|---|
| `architecture/02`、`harness/README` | "原生层无行为变化" | `crates/ragfs/src` **34 文件 / +4481−1083**、`crates/ragfs-python/src/lib.rs` +431−71 |
| `vfs/` ×6（含 README） | "v0.5.0 未改动这一层" | 同上；且**锁子系统长出了第三个后端** |

真正的洞见是这个错误**自带伪装**：它旁边列的结构件（洋葱顺序、7 插件、`chmod` no-op、`MoveFileExW`）**全部核对无误**。核对过一半就宣布了整体——这是"抽检通过 → 全称结论"的典型滑坡。

### 2.3 顺着锁后端查下去，查到一条真正的架构变化

`crates/ragfs/src/lock/cache_provder.rs` 是全仓最大新增文件（内容 1869 行）。顺着它查：

- `lock/mod.rs:27` 导出 `RedisPathLockProvider`
- Python 侧 `agfs_config.py:308-348`：`provider` 从 `filesystem | memory` 变成 `filesystem | memory | cache`，`cache` 必填 `namespace`（限 ASCII 字母数字与 `._-`）
- Redis 侧的原子性靠 **9 个 Lua 脚本**（`pathlock.acquire_batch.v1`、`compare_write.v1`、`scan_descendants.v1`…），活性靠 `PEXPIRE`（`:254,311`）+ hash 兜底 TTL = `2 × lock_expire_secs`（`:471`）

**为什么这条重要**：`vfs/` 原来那套"token 侧车文件 + TTL，与平台无关"的描述，其隐含前提是**本地文件系统是锁的唯一真相**。`cache` 后端把这个前提打掉了——现在多实例部署可以共用一套 Redis，锁真正能跨机器。这不是新增一个可选项，是**锁的作用域从"单机"扩到了"一个 namespace"**。

### 2.4 重写 `localfs` 顺带拆掉了一个外部依赖

`localfs/mod.rs` 重写 819 行，直接原因是 grep：v0.4.19 会在构造时探测 `PATH` 里有没有 `rg`（`has_rg`），有就 spawn `rg --json` 子进程，没有才退回进程内实现。v0.5.0 **把整条外部路径删了**——全文件已无 `Command::new`，进程内 `grep_via_libs`（`:418`）成为唯一路径，上下文收集抽到新模块 `core/grep.rs`（`GrepLineCollector`）。

方向判断：这是**去外部依赖**的收敛，行为一致性变好（不再受宿主机装没装 rg 影响），代价是丢掉 rg 的 SIMD 优化。**原文那句"生产代码跨平台"的方向反而更成立了，但依据换了**——这种"结论对、理由错"的漂移最容易在复核里被放过。

## 三、复核结论总表

### 仍然成立的强结论（改动时别误删）

`vfs/`：PathLock 不是 byte-range 文件锁、`chmod` no-op、Windows `MoveFileExW` 覆盖语义、`_shorten_component` 255 字节截断、大小写/保留名零防护、就地写无 temp+rename、`\\?\` verbatim 来自 `canonicalize`。

`harness/`：四处封闭枚举的封闭性（URI scope / 内容类型 / L0-L1-L2 / 合并策略）、三档接缝开放度排序（provider > ingest > parser）、`CONTRIBUTING` 的"默认不加单测"哲学、`_test_full.yml` 是孤儿 workflow、`README.md:111` 的 0.3.22 漂移、根目录无 ~~`AGENTS.md`~~。

### 需要记着的异常

1. **`app.py:793-833` 越界**（旧锚点，已修正为 `:744-786`）——文档引用的行号超过了文件长度。这是 OOB 检查存在的全部理由。
2. **`parse/registry.py` 与不存在的 `parse/parsers/registry.py`** 极易混淆，已在 1.3 标注。
3. **测试文件数有三套口径**：全仓 795、`tests/` 下 730、`tests/` 下 `test_*.py` 728。引用必须带口径。

## 四、给下一轮的规矩

1. **同步轮的最后一步必须是"把 000N 的影响表压回正文"**，而不是写完台账就收工。0002 与 vfs 正文互相矛盾的根因就在这。
2. **"某层没变"必须给出反面证据才算数**：不是"我看了觉得没变"，而是"该目录 `git diff --stat` 是 0"。给不出这个数就不许写这句话。
3. **锚点检查器先跑**，再开始读文档。
4. **纯数量断言（N 个文件 / N 行 / N 个枚举）必须当轮实测**，不许从上一轮抄——本轮 655 vs 730、32 vs 31、1.2 的 6/26/15 都是抄出来的。**同一篇里只要有一个数重算了，其余数就更容易被误当成已核**——这是本轮最隐蔽的一类错误：282→319 认真重算了，紧挨着的 6/26/15 原样留着。
5. **复核的产物本身要按被复核对象的标准自查**。本轮的第一批复核块写进了 9 篇的锚点汇总之后、3 篇的状态标注之后，把全文档集统一的章节模板打断了；还有一篇把"内容解析"当成第三个接缝写进导语，与正文三个判断冲突。**修文档的人最容易犯的错，是只检查内容不检查结构。**

**代理报错了两条，我驳回**（说明审计代理本身也要被审计）：
- "`--wait` 只等于被弹出一次"——`is_complete` 要求 `pending_semantic_roots` 与 `pending_embedding_roots` 双清（`request_wait_tracker.py:257-264`），文档描述是对的。

**两条方法论结论**（比上面任何一条错误都重要）：

1. **"25 个 router" 同时存在于三个文档里，而且其中一处还写着"2026-09-13 修正：此前写 26 个"**——说明它被修正过，但每次都是对着上一份文档改，不是对着代码改。**一个错误的数会在文档之间互相印证，越传越像真的。**
2. **同一个词在两层指两个东西时，最容易出错**：注册表里的工具数 vs 模型能调用的工具数；pyo3 方法总数 vs `pathlock_*` 方法数；文件数 vs 变更文件数。这类错误检查器一律看不见，因为**行号是对的，只有量词是错的**。

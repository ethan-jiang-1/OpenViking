## 二、这轮做了什么

### 2.1 先把校验做成工具，而不是做成一次性的手工核对

`_digested/_tools/check_anchors.py`：把两个文档目录里所有 `文件:行号` 锚点解析到工作树，报两类失效——NOFILE（文件已不存在）与 OOB（文件比引用行号短）。墓碑（指向已删除机制的锚点）按行内标记豁免。

首跑 **688 个锚点 / 3 个真失效**，修完归零（`7b3488d96`）。3 个失效里 1 个是 `integration-evidence` 把 Web Studio 块写成 `app.py:793-833`（旧锚点），而该文件总共 812 行——**引用越过了文件末尾**，纯手工核时看不出来。

它的价值不在于功能复杂，而在于**它让"锚点腐烂"从主观变成可回归**。以后的同步轮第一步就该是它。

### 2.2 抓住那个最贵的错误："某层没变"

"某层没变"是所有断言里最容易写、最难查、破坏力最大的一种：

- 它**不指向任何一行代码**，所以锚点检查器抓不到它；
- 它会**连带作废一整篇的立论前提**；
- 它读起来像谨慎（"我确认过了，没动"），实际是**概括性偷懒**。

本轮抓到两处，同一根源：

| 位置 | 原话 | 实测 |
|---|---|---|
| `architecture/02`、`harness/README` | "原生层无行为变化" | `crates/ragfs/src` **34 文件 / +4481−1083**、`crates/ragfs-python/src/lib.rs` +431−71 |
| `vfs/` ×6（含 README） | "v0.5.0 未改动这一层" | 同上；且**锁子系统长出了第三个后端** |

真正的洞见是这个错误**自带伪装**：它旁边列的结构件（洋葱顺序、7 插件、`chmod` no-op、`MoveFileExW`）**全部核对无误**。核对过一半就宣布了整体——这是"抽检通过 → 全称结论"的典型滑坡。

### 2.3 顺着锁后端查下去，查到一条真正的架构变化

`crates/ragfs/src/lock/cache_provder.rs` 是全仓最大新增文件（内容 1869 行）。顺着它查：

- `lock/mod.rs:27` 导出 `RedisPathLockProvider`
- Python 侧 `agfs_config.py:308-348`：`provider` 从 `filesystem | memory` 变成 `filesystem | memory | cache`，`cache` 必填 `namespace`（限 ASCII 字母数字与 `._-`）
- Redis 侧的原子性靠 **9 个 Lua 脚本**（`pathlock.acquire_batch.v1`、`compare_write.v1`、`scan_descendants.v1`…），活性靠 `PEXPIRE`（`:254,311`）+ hash 兜底 TTL = `2 × lock_expire_secs`（`:471`）

**为什么这条重要**：`vfs/` 原来那套"token 侧车文件 + TTL，与平台无关"的描述，其隐含前提是**本地文件系统是锁的唯一真相**。`cache` 后端把这个前提打掉了——现在多实例部署可以共用一套 Redis，锁真正能跨机器。这不是新增一个可选项，是**锁的作用域从"单机"扩到了"一个 namespace"**。

### 2.4 重写 `localfs` 顺带拆掉了一个外部依赖

`localfs/mod.rs` 重写 819 行，直接原因是 grep：v0.4.19 会在构造时探测 `PATH` 里有没有 `rg`（`has_rg`），有就 spawn `rg --json` 子进程，没有才退回进程内实现。v0.5.0 **把整条外部路径删了**——全文件已无 `Command::new`，进程内 `grep_via_libs`（`:418`）成为唯一路径，上下文收集抽到新模块 `core/grep.rs`（`GrepLineCollector`）。

方向判断：这是**去外部依赖**的收敛，行为一致性变好（不再受宿主机装没装 rg 影响），代价是丢掉 rg 的 SIMD 优化。**原文那句"生产代码跨平台"的方向反而更成立了，但依据换了**——这种"结论对、理由错"的漂移最容易在复核里被放过。

## 四、给下一轮的规矩

1. **同步轮的最后一步必须是"把 000N 的影响表压回正文"**，而不是写完台账就收工。0002 与 vfs 正文互相矛盾的根因就在这。
2. **"某层没变"必须给出反面证据才算数**：不是"我看了觉得没变"，而是"该目录 `git diff --stat` 是 0"。给不出这个数就不许写这句话。
3. **锚点检查器先跑**，再开始读文档。
4. **纯数量断言（N 个文件 / N 行 / N 个枚举）必须当轮实测**，不许从上一轮抄——本轮 655 vs 730、32 vs 31、1.2 的 6/26/15 都是抄出来的。**同一篇里只要有一个数重算了，其余数就更容易被误当成已核**——这是本轮最隐蔽的一类错误：282→319 认真重算了，紧挨着的 6/26/15 原样留着。
5. **复核的产物本身要按被复核对象的标准自查**。本轮的第一批复核块写进了 9 篇的锚点汇总之后、3 篇的状态标注之后，把全文档集统一的章节模板打断了；还有一篇把"内容解析"当成第三个接缝写进导语，与正文三个判断冲突。**修文档的人最容易犯的错，是只检查内容不检查结构。**
6. **改矛盾的一端之前，先 `grep` 出这一条事实的所有副本。** 第五轮的四个缺陷全是半修：表头改了正文没改、正文改了锚点汇总和评审表没改。**半修比不修更危险**——它让文件同时断言两件互斥的事，而读者无从判断该信哪个。改任何一条被多处重复的事实，先 `grep -n "<那句话的独特片段>"` 数清副本数，再逐个改完。
7. **打了 ✅ / 【硬事实】 / 复核过的断言，下一轮必须重验。** 通行证是叫人停止检查的东西，而它恰恰贴在最该重验的地方——第五轮那个错锚点的评审表就打着 ✅。**状态标注不是免检章，是欠条。**
8. **证据文件（`_notes/*.md`）必须被它服务的每一篇正文链接。** 更正通常先落在证据文件里，正文滞后；没被链接的证据文件等于不存在。第五轮发现全集最大的证据文件（104k 字符）只被 1 篇引用，而消费它全部数字的两篇一处都没链。

### 5.2 最值得记的两条

**一、`heartbeat` 从未存在。**
`2.2` 把"`heartbeat` 被删除，由 watch+TTL 取代"和"`/used` 被删除"并列，作为"v0.5.0 已实打实发生两次"的证据。
实测：`git grep -rn heartbeat v0.4.19 -- openviking/` **零命中**，当前树同样零命中——**不存在的东西不能被删除**。
而 `/used` 是 **`v0.4.22`**（`676a8954f`）删的，比 `v0.5.0` 早两个版本。**两条证据，零条成立。**
它的每个行号都可以是对的，结论却完全错——这是"锚点正确"与"论证有效"之间的最大鸿沟。

**二、三个审计代理各自推翻了自己前一版结论。**
`a7096f28` 连发三版，v3 明确撤回 v1/v2 的 5 条（64 个 tag 是对的、openGauss 锚是对的、workflow 算术是对的、tombstone 跳过的范围被夸大了）。
**这是这套流程里最有价值的信号**：代理会出错，但**带命令的代理会自己纠错**，而"我记得它变了"不会。

### 5.3 落地的结构性修补

1. **`_digested/_tools/REVIEW_PROTOCOL.md`**——把八种已发生的缺陷类型固化成人工清单，每条带真实案例和一行 grep 查法。
2. **`check_anchors.py` 补了两类真盲区**：裸路径（此前 `skills/.../SKILL.md` 完全不可见）与软 tombstone（`不存在`/`已删除` 曾让整行免检，而那正是最该检查的行）。

### 5.4 这一轮的教训

> **一个错误的版本归因，会让整段论证失效，而它的每个行号都可以是对的。**

> **检查器全绿 ≠ 文档正确。** 守卫必须覆盖缺陷真正发生的维度，否则绿灯只是"没在看"。

> **"在某版本 X 中变了"是本套文档最脆的句式。** 它要求同时正确：变了什么、在哪一版变、现在是什么。
> 三者中任一错，整句作废——而它通常只有一个行号，看起来最可靠。

## 六、第五轮：审计我自己（2026-10-19 深夜）

第四轮改了 63 个文件、1145 行插入。**统计上，最可能有缺陷的文档就是上一轮刚改过的那些**，所以第五轮从自己的 diff 开始。

### 7.1 最贵的一类：半修

> **把矛盾的一端改对、另一端留着，比两端都错更糟。**

因为两端都错时文件只断言了一件错事；半修之后它同时断言两件互斥的事，读者无法判断该信哪个。

| 半修 | 表现 |
|---|---|
| `_notes/discipline-selfdescription-evidence.md` | 表头改成 31/730，正文三处仍是 29/655 |
| `4.2_docs_for_agents.md` | 正文改成 `README.md:57`，锚点汇总和评审表仍写 `:48-49`——**一条事实三种口径，其中一条还打着 ✅** |
| `_notes/vfs-platforms-evidence.md` | 表头声明"全部仍有效"，§1–§2 锚点整组停在旧基线 |
| `integration/02` | 撤回声明写"整组行号都是旧的"，实测命令清单表是旧的、结构/旗标锚点却是新的 |

那个 ✅ 尤其危险：**正是它让我停止检查**。上一轮我把 4.2 报成已修，实际上三份副本只修了一份。

### 7.2 分项与总数不同源

`discipline` 正文列出九个测试子目录（sum = 514），同句声称总数 655。**差额被一个"等"字掩盖了**。
这类错误的形状是：总数从一处取，分项从另一处取，两边从没对过。

### 7.3 复盘文档自己腐化

`REVIEW_PROTOCOL.md` 是第四轮写的，**一轮之内**，它引用的四个案例行号全失效了（因为它引的正是它要修的那些文档）。
一份专门警告"行号会漂"的文档，以行号漂移的方式失效。已改为按引文内容锚定。

### 7.4 证据链断裂

`_notes/discipline-selfdescription-evidence.md` 是全集最大的文件（104k 字符），
而**消费它全部数字的 `4.1`/`4.2` 两篇，一处都没链它**——只有 `3.1` 链了。
未被链接的证据文件不做任何工作；更糟的是**更正通常先落在那里**，正文滞后，于是"知道答案的地方"对提问的页面不可见。

### 7.5 问题文件的不合时宜

`_faq_on_digested/05` 的 `question.md` 第 3 问是"怎么利用目录递归"，
而递归在 `v0.5.0` 已被删除。`answer.md` 早已更正并带反转记录，**但问题文件没有**，
而问题文件是目录里的第一个文件、读者的天然入口。

处理方式：**问题原文保留**（它是当时真实提出的问题，改写等于抹掉历史），
顶部加带日期的提示，并把已失效的两个机制划掉。
**一个问题可以正当地过时，但不能悄悄地过时。**

### 7.6 checked-by-whom：检查器按单模板编写会误判

第五轮我写了个结构检查脚本，规则是"复核块必须在 `## 状态标注` 之内"——**因为那天我在 harness 里泡着**。
结果它把 `integration/02` 本来正确的独立 H2 判成结构错误，我还真的动手改了。

而本目录有**三套模板**：`core/`/`vfs/`/`integration/`/`architecture/` 用独立 `## v0.5.0 复核` H2；
`harness/` 9 篇用合并式；FAQ 末章是 `## 反转记录`。

更值得记的是：`vfs/03` 形态与之相同却**没被报**——它的标题是"`## v0.5.0 复核：grep 的外部依赖被拆掉了`"，
我的正则只认"复核结论"。**所以这个错检器同时干了两件坏事：改坏了对的，放过了错的。**

> **一个只见过一种模板的检查器，会把那种模板认成唯一正确的。**
> 写结构检查前先读模板表；不确定时报告，不要自动修。

### 7.6 这一轮的教训

> **半修比不修更危险。** 改矛盾的一端之前，先找到另一端的所有副本。

> **✅ 是叫人停止检查的东西。** 凡是打了通过标记的断言，下一轮最该重验。

> **证据文件必须被它服务的正文链接。** 否则更正进不去。

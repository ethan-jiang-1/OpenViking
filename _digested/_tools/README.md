# _tools — 文档自检工具

## `check_anchors.py`

把 `_digested/` 与 `_faq_on_digested/` 里所有 `文件:行号` 形式的锚点解析到工作树，检查两种机械性失效：

- **NOFILE**：全树找不到该文件名的源文件（文件被删或改名）
- **OOB**：文件存在但比引用行号短（文件被大幅改写／删减）
- **BADPATH**：全文任何一个文件都不以该锚点的**目录前缀**结尾（例如 `parse/parsers/registry.py`——`registry.py` 确实存在，但在 `parse/` 下，不在 `parse/parsers/` 下）。**这一项是 2026-10-19 补的**：此前只比对 basename，于是"文件对、目录错"的锚点全部漏检，包括本套文档自己写出来的一个。

```bash
python3 _digested/_tools/check_anchors.py           # 报告
python3 _digested/_tools/check_anchors.py --strict  # 有发现则非零退出
```

**它是"边界检查"不是"语义检查"**——通过的锚点仍可能指错东西。它只负责拦住锚点腐烂里最廉价、也最容易悄悄积累的那一半。

## 墓碑约定

指向**已在 upstream 删除**的机制的锚点是有价值的（它记录了"这里曾经有什么"），不该被当成错误。在同一行写上下列任一标记即可让检查器跳过：

`~~`（删除线）、`旧基线`、`已删除`、`被删`、`不存在`、`旧锚点`、`已缩到`、`旧分支`

## 它看不见什么（重要）

1. **`符号(:NN)` 裸行号**：`mcp_endpoint.py` 里有一整段写成 `` `find`(:249) ``，没有文件名，检查器完全看不到。该段在 `v0.5.0` 已整体漂移（`:249` 实际应是 `:449`），是靠手工复核才发现的。**取证请一律写 `文件:行号`。**
2. **语义**：锚点行号对、但那一行讲的是别的事——检查器无从判断。
3. **"某层没变"类断言**：这类句子不指向任何一行代码，却是本套文档里代价最高的一类错误（见 `_change_log/0003`）。
4. **引号里的"官方原话"**：检查器只验锚点是否可达，不验那一行**真的包含**你引的那句话。`architecture/02` 曾把一个压根不存在的官方句子挂在一个真实行号上，检查器全绿。**引号内容是纯人工责任**——这也是本套文档里出现过的最严重缺陷类型。
5. **量词**：`52 个方法` 和 `52 个 pathlock_* 方法` 里行号可能完全正确，只有量词错。检查器看不见量词。

> **一条元规则**：检查器"全绿"与"没在运行"看起来一模一样。因此**每次新增一类检查，都必须先造一个已知错误输入、确认它真的报警**。2026-10-19 的裸路径检查加了四轮才生效，前三轮都在静默返回 `no findings`（详情见提交 `tool(check_anchors)` 的 message）。

## 历史

2026-10-19 首次运行（分支 rebase 到 `v0.5.0` 之后）：688 个锚点里 3 个真失效（2 个指向已删的 `semantic_dag.py`、1 个 `app.py:793-833` 越界）——全部修复后归零。在此之前这些检查做不了，因为工作树与文档基线不是同一个版本。

同日晚些时候的复核轮：加入 **BADPATH** 后立刻抓到 `_notes/integration-evidence.md` 的 `integrations/langchain/pyproject.toml`（真实位置 `examples/langchain/`）。当前基线：**63 篇 / 699 个锚点 / 0 失效**。

2026-10-19 第三轮：补齐**裸路径检查**（不带 `:行号` 的 `文件.py` 引用）。此前这类写法是完全的盲区——`skills/openviking-memory/SKILL.md` 靠它混过了若干轮复核，真实路径是 `agent-plugins/skills/openviking-memory/SKILL.md`。同时把 37 处"断言某路径**不存在**"的引用标成 tombstone（`~~` 或 `该文件不存在`），避免新检查把它们误报成失效锚点。当前基线：**63 篇 / 721 个定位锚点 + 326 个裸路径 / 全部通过**。

2026-10-19 第四轮（四个只读审计代理分片复核）：检查器全程 **0 findings**，而这一轮找出 **40+ 个真缺陷**——**没有一个**在它的覆盖范围内。当前基线：**65 篇 / 795 个锚点 / 398 个裸路径 / 0 硬失效**（58 处软 tombstone 跳过）。

这一轮的结论不是"再加一条规则"，而是承认了结构性事实：**这个工具管"能不能到达"，不管"到达的地方是不是那句话"。**它验证路径存在与行号范围；而缺陷发生在内容层——伪造的引文、两个版本前就被删的引文、反向的"仓库里没有 X"断言、错误的版本归因、自造的代码分类法。八种类型连同真实案例已写入 [`REVIEW_PROTOCOL.md`](./REVIEW_PROTOCOL.md)，那是给复核实的人用的清单，不是机器门禁。

**为什么不做机器引文校验**：可以抽引号内文本去 `grep -F`，但中文引号既用于逐字引用也用于转述，误报率会高到没人看——一个被忽略的红灯和一个不存在的红灯效果相同。所以引文校验保持人工，并且**每条引文都必须能指出它在被引文件里的位置**。

**元规则（本轮的产出）**：任何新增的机器检查，都必须先造一个已知错误输入证明它会报警。否则你无法区分"检查通过"和"检查没在跑"——本工具就曾因为 `ANCHOR_RE.search("`" + cited + ":1`")` 恒真，把裸路径检查静默跳过了三轮（`bare_total` 从 123 跳到 326 才暴露）。

2026-10-19 第五轮：新增 [`check_half_fixes.py`](check_half_fixes.py)——**半修检测器**。

**为什么需要它**：`check_anchors.py` 保证"路径能到达"，但它看不见**同一句断言在多处副本之间已经不一致**。第五轮找到的缺陷里，四个是同一形态：

| 半修 | 一端改了 | 另一端没改 |
|---|---|---|
| `discipline-evidence` | 表头 31/730 | 正文三处 29/655 |
| `4.2_docs_for_agents` | 正文 `README.md:57` | 锚点汇总 + 评审表 `:48-49`（**带 ✅**） |
| `2.2` 的 `heartbeat` | 正文已撤回 | `harness/README`、`02-Boundaries/README`、证据台账仍在断言 |
| `4.1` 的"无一处需要改" | 两处单独更正 | 那句绝对断言本身还在 |

**用法**：

```bash
python3 _digested/_tools/check_half_fixes.py --quiet          # 跑内置撤回清单
python3 _digested/_tools/check_half_fixes.py --phrases "某短语"  # 指定短语
```

判定：含某短语的行若同时含撤回标记（`撤回`/`~~`/`从未`/`已删`/`实为`/`曾写`/`编的`…）则跳过，否则报"未标注残留"。

**已知局限（与 `check_anchors.py` 的盲区同源）**：

1. **不读语义**——分不清"X 是错的"和"X 是正确的"。引述别人错误以撤回它的行会被误报（实测 5 个命中里 4 个是这类）。
2. **短语人工给**——它不知道哪些断言被撤回过。内置清单是本套文档的已知账，新撤回要手动加。
3. **台账类文件天然误报**——`_change_log/` 里"X 被删除"是正确用法，不是残留。

所以它是**复核辅助，不是门禁**。但按元规则，它已用已知错误输入验证过会报警：

```
$ printf '# 测试\n\n这里断言 heartbeat 删除 是事实。\n' > 探针
[1 处未标注] heartbeat 删除
   …:3  这里断言 heartbeat 删除 是事实。
exit 1
```

**这一轮把元规则坐实了**：`check_anchors.py` 曾连续三轮静默失效（`ANCHOR_RE.search` 的守卫恒真），
`check_half_fixes.py` 的第一版也因为标记词太少而误报 4/5。**绿灯只有在它被证明会变红之后才有意义。**

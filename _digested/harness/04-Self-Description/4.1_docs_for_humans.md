# 4.1 给人的文档：IA 是资产，口径是负债

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 的文档体系分四处：官方 docs 站（`docs/en|zh`）、三份 CONTRIBUTING、`RELEASE.md` 发布指南、`docs/repository/`（多语言 README/RELEASE 的存放处）。逐处核对覆盖度与一致性后，IA 质量与口径纪律呈现明显反差。

> **v0.5.0 结构性变化（2026-10-19）**：**`docs/design/` 整个被删除**（含 21 份设计稿与 `l0-l1-okf-sidecars-rfc.md`），`docs/plans/`、`docs/superpowers/`、`docs/WeChat_article/` 一并消失；根目录的 `README_CN.md`/`README_JA.md`/`CONTRIBUTING_CN.md`/`CONTRIBUTING_JA.md`/`RELEASE_CN.md` 全部移到 `docs/repository/`。官方 docs 站只剩 **en + zh** 两个语种（`docs/ja` 不存在），两栏各 **110** 个 md 文件，完全对齐。

## 核心矛盾是什么

**文档广度 vs 口径维护成本**：三个语言版本 × 17 篇集成文档 × 8 个发布物的版本口径，任何一处事实变化都要多处同步。OpenViking 把广度做到了罕见水平，但同步机制的缺失已经开始产生可观察的漂移。

## 设计判断是什么

### 判断 1：概念文档的 IA 是教科书级，且三语齐平【硬事实】

- `docs/en/concepts/` **18 篇**（v0.5.0：16 → 18，新增 `16-queue-lifecycle.md`，并前置了 `00-overview.md`）：overview → architecture → context-types → context-layers → viking-uri → storage → extraction → retrieval → session → transaction → encryption → multi-tenant → metrics → privacy → multi-write-storage → acl → vikingbot → queue-lifecycle——**从模型到机制到运维的顺序严格递进**，没有孤儿篇。注意 `15-acl.md` 与 `15-vikingbot.md` **编号撞车**（同一序号两个文件），是新引入的小瑕疵
- 双语覆盖不止 concepts：en/zh **各 110 个 md，逐栏目完全镜像**（v0.5.0 实测；建档基线为 93/94）——开源项目里少见的非英语全量翻译
- **19 篇** `agent-integrations/`（v0.5.0：17 → 19，新增 `18-plugin-development.md`、`19-recall-tuning.md`）以"如果你用 X 就选 Y"的决策表开篇（`01-overview.md:5-22`），并维护 **820 行**跨集成能力对照矩阵（`16-capability-reference.md`）——**官方自己维护 parity 表**是自描述的最高形态
- quickstart 可信度抽查通过：`openviking-server init/doctor` 对上 `server_bootstrap.py:84-88`，`ov` 子命令对上 `crates/ov_cli/src/main.rs:2453`——命令文档与源码逐条可验（取证报告 B3）

评价：概念层的自描述质量高于 pi-mono（pi 的 docs 随包走、无统一概念层，`_digested` 里要靠自己的 06-coverage 表补位）。这张官方 parity 表也是本仓库 `_digested/integration/` 选择"核验而非重写"策略的原因。一处保留：README 的 benchmark 数字（82.08% 等）在仓库内 grep 不到——`benchmark/` 复现脚本存在（"可复现"成立），但数字本身闭环在博客（"数字可核"不成立）。

**判断 1 的 v0.5.0 补充（负面）**：**`docs/design/` 的删除是一次自描述资产的净损失**。那 21 份设计稿里至少有一份（`l0-l1-okf-sidecars-rfc.md`）描述的是**已实现且在主路径上的存储格式**——它的消失意味着"L0/L1 sidecar 为什么长这样"在官方文档里再无一手来源，只剩代码。同批消失的 `docs/plans/`、`docs/superpowers/` 也不留归档路径。**这是把历史证据当仓库卫生清掉的决定**，对本项目这类要判断"设计意图 vs 现实漂移"的工作，代价是实打实的。

### 判断 2：口径漂移已经发生，且恰好在最显眼处【硬事实】

- 根 README 自述 "OpenViking **0.3.22** has been evaluated on LoCoMo..."（`README.md:111`），而 release tag 已到 **v0.5.0**——**这个偏差从 v0.4.19 一路带到 v0.5.0，跨了两个大版本没人改**。v0.5.0 只是把多语 README 合并成一份主文件（`docs/repository/` 保留 CN/JA 版本），**没有修数字**。旧文说"三份同病"，现在是"一份仍在病"——问题的形状变了，问题没解决
- ~~`docs/design/l0-l1-okf-sidecars-rfc.md` 标 Draft，但其存储格式已实现并被主路径使用~~——**v0.5.0 已把这份 RFC 连同整个 `docs/design/` 删除**。旧问题（状态标记与实现脱节）以"删掉文档"的方式消失了，代价见判断 1 的补充。L0/L1 sidecar 的现行事实只能从源码读（[`core/02`](../../core/02-context-layers.md) 已做此事）
- 有趣的对照：`RELEASE.md` 的版本口径反而最准（明确给出 `vX.Y.Z` / `python-sdk@X.Y.Z` 双命名空间，且自述基于 workflow 追踪）——**离 CI 越近的文档越准，离营销越近的文档越漂**

评价：口径漂移的根因不是没有守卫能力——`docs/scripts/check-api-reference.mjs`（API 文档 ↔ server 路由双向一致性）就是进了 CI 硬门禁的机器守卫（`_docs.yml:36-38`），**但它只保护 API 参考这一层**；普通 markdown 被 `pr.yml` 的 paths-ignore 排除在 PR CI 外。README 的版本号是一个没有任何东西守护的字符串——守卫有了，覆盖面没跟上。

> **v0.5.0 更新**：文档守卫已扩到**四道**（`_docs.yml`：theme 测试 `:28-30`、`check:docs` 双语+examples 一致性 `:32-34`、`check:api` API 参考 `:36-38`、`check-built-anchors.py` 构建后锚点 `:46-49`）——**覆盖面确实在长**。但 `README.md:111` 的 0.3.22 依然没被任何一道拦住，证明"有守卫"和"守住关键数字"仍是两件事。

### 判断 3：design 稿文化"有库、有回写、无状态机"【硬事实 + 解释】（初稿判断已细化）

`docs/design/` 曾有 21 份设计稿。状态标记**四种格式并存**："Status: Draft"、"> 状态: Draft"、中文值 "Status: 已批准进入实现"、以及表格内"历史设计，现行方案见下方说明"（自我宣布过时，说明有回写机制）；约半数无状态字段。设计↔实现有活引用与对应代码（okf-sidecars ↔ `abstract_overview.py`、cuVS 设计 ↔ `vectordb/` 适配器、usage_reporter 均有实现），文档间引用链接有效。

**v0.5.0：整个目录被删除**，上述观察从此只能作为历史记录存在。

评价：比初稿判断的"无状态机"更准确的说法是：**内容上有回写文化（会自我宣布过时），机器可读性上无统一 lifecycle 元数据**——人和 AI 都只能靠读全文判断哪份是现行设计。pi-mono 后期给 harness.md 加 §implementation-status 清单正是补这一层，OpenViking 的 21 份设计稿是现成的应用场景。

## 影响是什么

- 对使用者：概念文档可以放心信，**版本号和 design 稿状态不要直接信**——前者查 tag，后者按 [`core/02`](../../core/02-context-layers.md) 的方法对照源码。
- 对上游：性价比最高的两个修复：① README 版本口径改为引用 tag 或 RELEASE.md（消灭三份文档的同步负担）；② RFC 加 §implementation-status（一次性成本，永久止血）。

## 源码锚点汇总

- `docs/en/concepts/`（18 篇）与 `docs/zh/concepts/`（18 篇）对照；`en`/`zh` 各 110 个 md
- `docs/en/agent-integrations/01-overview.md:5-22`、`16-capability-reference.md`（820 行，19 篇目录）
- 根 `README.md:111` "0.3.22" vs `git tag` v0.5.0；`docs/repository/`（CN/JA 版本）；`_docs.yml:28-49`（四道文档守卫）

## 最小例证

搜索 `0.3.22`：`README.md:111` 命中且无人报警（四道文档守卫都不看这一行）；同法搜 `OVPACK_FORMAT_VERSION`：定义处单一、import 处强校验。同一仓库里两种事实的命运差异即本文判断。**v0.5.0 把这行从三处合并到一处，但仍未守护——修了一张脸，没装报警器。**

# 4.2 给 agent 的自描述：产品为 agent 而生，仓库却没对 agent 说话

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 的产品定位是"给 AI agent 当上下文后端"，它的**运行时**对 agent 的自描述相当完整；但**仓库本身**——贡献者要面对的那一层——没有任何面向 AI 的入口文件。产品与仓库在"对 agent 说话"这件事上严重不对称。

## 核心矛盾是什么

**agent 是用户，也是贡献者**：OpenViking 的 runtime 把 agent 当一等用户服务（工具、技能、召回），但当一个 agent（或用 agent 干活的贡献者）走进这个仓库想改代码时，迎接它的是零份 AI 可执行的指南。

## 设计判断是什么

### 判断 1：运行时的 agent 自描述是模范级的【硬事实 + 解释】

- `agent-plugins/skills/openviking-memory/SKILL.md` 的 frontmatter description 一段话里写清了：何时用（"start of any substantive task"）、怎么用（find/search/read 召回 + remember 持久化）、**何时不该用**（"Do not use for casual chat or simple factual questions the model can answer directly"）——反面边界进 description 是 skill 写作的最佳实践，多数项目的 skill 只写正面用法
- SKILL.md 正文同样明示能力边界："This client has no lifecycle hooks, so nothing is recalled or captured automatically — **you drive both halves of the loop**"（`skills/openviking-memory/SKILL.md:9-11`）；插件 README 用自己的措辞说同一件事："deliberately excludes hooks… automatic conversation capture and automatic pre-prompt recall are out of scope here"（`agent-plugins/README.md:48-49`）——把 agent 的责任边界说到了动词级（2026-09-13 修正引文归属：此前版本把 SKILL.md 的句子锚到了 README）
- **19 篇**集成文档 + capability matrix（v0.5.0：17 → 19，权限表 737 → 820 行）本质上是给"配置 agent 的人"的完备决策材料

评价：这说明团队**完全有能力**写出 agent 可执行的自描述——SKILL.md 的质量证明不是不会写。那么仓库层的缺位就更加耐人寻味。

### 判断 2：仓库层零 AI 入口，与贡献哲学形成未闭合的环【硬事实 + 解释】

- 根目录无 `AGENTS.md` / `CLAUDE.md` / `.cursorrules` / `GEMINI.md` / `.clinerules`（**v0.5.0 复核：`git ls-tree -r v0.5.0` 仍然零命中**——本文的预测"v0.5.x 前后会出现根级 AGENTS.md"到目前为止**没有被证伪，但也还没被证实**）；存在的 AI 相关文件只有两个，且都不是给贡献 agent 的：`.claude-plugin/marketplace.json`（**分发**清单）和 `.pr_agent.toml`（17KB，给 **PR-Agent 审查者**的规则——团队会为 AI 写规则，但服务对象是 review 流程，不是进仓库干活的 coding agent）
- 对照 `CONTRIBUTING.md`：它明确预期 AI 参与贡献（"Contributors are responsible for understanding, explaining, and validating their changes, **whether or not AI tools were used**"），并且把贡献哲学写到了"Avoid speculative fallbacks, flags, state fields"这种**可直接进 system prompt**的粒度——素材已经存在，只差一份面向 AI 的汇编与入口
- 对照 [3.1](../03-Discipline/3.1_ci_guard_chain.md)：`pr.yml` 把 `**.md` 全部排除在 CI 外——即使明天补上 AGENTS.md，也没有机制防止它腐烂。v0.5.0 给 `docs/` 加了三道守卫（双语/API/锚点），**但这条"md 不进 PR CI"的口子没关**，所以判断 2 的结论不变

评价：这不是疏忽，更像是**刻意极简**（与 core-minimal 纪律一致：不加没有守卫能力的文件）。但 pi-mono 的经验给出了反面证据：AGENTS.md 恰恰是 AI 贡献时代性价比最高的自描述载体——OpenViking 的贡献哲学是现成的 prompt 素材，只欠一个入口。本文预测（可证伪）：v0.5.x 前后会出现根级 AGENTS.md，触发点大概率是外部 AI 贡献第一次违反"What We Value"里的某条。

> **v0.5.0 的相反动作**：不但没加 AGENTS.md，还把 `docs/design/`（21 份设计稿）整批删了。这更坐实了"刻意极简"的读数——**团队的方向是减少仓库内的说明性资产，而不是增加**。本文预测的证伪窗口可以收紧到 v0.6.x。

### 判断 3：自描述的分层结构清晰，但层间互指缺失【硬事实 + 解释】

现有自描述按受众分布：人类使用者 → docs 站；agent 用户 → SKILL.md + 插件文档；人类贡献者 → CONTRIBUTING；发布运维 → RELEASE.md（CN 版已移入 `docs/repository/`）；**v0.5.0 新增第五层：插件开发者 → `docs/en/agent-integrations/18-plugin-development.md`**。**唯独"进入源码的 AI 贡献者"一层没有文档**——而这个层恰恰是上面四层的交汇点（需要读 CONTRIBUTING 的哲学 + RELEASE 的口径纪律 + docs 的机制事实）。

评价：补一份 AGENTS.md 的正确内容因此不是新写，而是**汇编既有四层的要点 + 指路**——这也符合他们自己的"Reuse the existing owner of a rule"哲学。

## 影响是什么

- 对 agent 生态：SKILL.md 模式（正面用法 + 反面边界 + 责任划分）值得抄走；它比"塞一段长 system prompt"更可维护。
- 对上游：仓库自描述补齐的顺序应该是：AGENTS.md（汇编，一天）→ 文档进 CI 的 paths-ignore 反转（半天）→ RFC 状态归档（见 4.1）。三件事做完，"给 agent 的自描述"就从模范级产品扩展到模范级仓库。

## 源码锚点汇总

- `agent-plugins/skills/openviking-memory/SKILL.md` frontmatter（正反用法 + 责任边界）
- `agent-plugins/README.md:48-49`（能力边界声明）
- 根目录 AI 文件零命中（`git ls-tree -r v0.5.0` 复核）；`CONTRIBUTING.md`（AI 责任句 + 可 prompt 化的哲学条目）；`pr.yml`（md 排除）；`docs/en/agent-integrations/18-plugin-development.md`（v0.5.0 新增的开发者向自描述）

## 最小例证

问一个接入了 openviking-memory skill 的 coding agent："这个仓库该怎么贡献？"——它会把 SKILL.md 的召回/持久化循环讲得头头是道，但对 CONTRIBUTING 的哲学条目一无所知（没有任何机制把这些条目送进它的上下文）。同一个 agent 的两种无知即本文判断的不对称。

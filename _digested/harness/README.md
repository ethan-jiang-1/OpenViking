# harness/ — OpenViking 作为 harness 平台的评价层

> **基线**：OpenViking `v0.5.0`（2026-10-19 全维度复核；建档基线 `0f77ab56`）。本目录是评价维度，与 [`core/`](../core/)（机制解剖）、[`integration/`](../integration/)（外部接入）、[`architecture/`](../architecture/)（实现边界）并列。

## 这是什么

`core/` 回答"viking:// 文件系统怎么运转"；`integration/` 回答"别的宿主怎么接进来"；`architecture/` 回答"三语言边界在哪"。

本目录回答的是**第四个问题**：**OpenViking 作为一个开源 harness 平台——结构优不优秀、好不好扩展、开发有没有纪律、对使用者（以及跑在它上面的 AI agent）自描述够不够。**

它不替代机制文档，而是在机制之上做评价：哪些接缝设计得好、为什么好，哪些边界是短板、对"开源吸纳新东西"意味着什么。

## 写作定调（评价视角，区别于 core/）

本目录是**评价文档**，不是机制文档。默认顺序：

1. `现象是什么` —— 读者 1 段内看懂"这篇在评价什么结构/行为"
2. `核心矛盾是什么` —— 至少两条互相拉扯的目标
3. `设计判断是什么` —— 评价核心：结构优不优秀、为什么；**硬事实 / 解释 / 推测分开标记**
4. `影响是什么` —— 对"开源吸纳新东西"或"作为 harness 平台"意味着什么
5. `源码锚点是什么` —— 至少 2 个有效文件/函数锚点
6. `最小例证是什么` —— 一个可验证的观察信号，能证明或反驳判断

执行要求：

- 规则只在本 README 定义，不在每篇正文重复"写作规范"段落。
- **不与 core/、architecture/ 重写机制**：引用对应篇章，只补评价。
- **硬事实与评价分开**：评价要落到具体锚点，不能空谈"优秀"。
- **锚点给"为什么"**：不只列文件，要说清这个文件里的哪处设计支撑了判断。
- **引用设计稿先验证**：`docs/design/` 是规格不是现状（pi-mono ~~`facets.md`~~ 教训），凡引用须注明实现状态。**⚠️ v0.5.0 起 `docs/design/` 整个目录已被 upstream 删除**——现在没有设计稿可引，历史判断只能看本目录与 [`_change_log/0002`](../_change_log/0002-v0.4.19-to-v0.5.0.md)。

## 与 pi-mono harness/ 维度的关系

四分法照搬自 pi-mono `_digested/harness/`（其宪法要求"统一用 codebase-design 词汇 + 真 seam 检验 / deletion test / design-it-twice"）。评价对象不同（pi 是 agent 引擎、OpenViking 是上下文数据库），所以具体评价问题不同——OpenViking 的核心评价问题是：**一个数据密集型 server 产品，能不能保持"极简核 + 插件长能力"的可演化性，以及它的多语言结构是不是资产而非负债。**

## v0.5.0 复核小结（2026-10-19）

四个子维度在 v0.5.0 上的净变化，一句话版：

| 子维度 | 变化 | 评价 |
|---|---|---|
| 1.1 扩展接缝 | adapter 白名单 5→6（opengauss）；MCP 15→20；官方对工具面的说法从"集中发布"改为"重连即见" | 哲学没变；第三种接缝（MCP）的"无版本信号"这次自己承认了 |
| 1.2 分层纪律 | 反向 import `openviking_cli` 282 → **319** 个文件 | **恶化**，两处破口都没动 |
| 1.3 数据接缝 | ingest source 6 → **8**（mimo、workbuddy） | **唯一真的长出扩展的接缝**，证明"公开装饰器"设计有效 |
| 2.1 封闭枚举 | 四个枚举**全部未变**；消费点迁移（层级过滤下沉到索引层） | 稳定——这正是封闭枚举该有的样子 |
| 2.2 版本契约 | `used` 删除、`heartbeat` 删除（无版本协商兜底）；ovpack v3 / index v1 未动 | **判断被两次兑现**：接口层的风险不是假设 |
| 3.1 CI 守卫 | 26 → **30** workflow；655 → **730** 测试文件；文档守卫 1 → **4** 道 | 局部改善；**主包单测仍不进 CI**（`_test_full.yml` 仍是孤儿） |
| 3.2 贡献门 | see 3.2 | — |
| 4.1 给人看 | `docs/design/` 整批删除；docs 收窄到 en/zh（各 110 md）；README 的 `0.3.22` **仍未修** | 扩张与收缩同时发生；最显眼的口径错误跨两个大版本没修 |
| 4.2 给 agent 看 | 根级 `AGENTS.md` **仍不存在**；新增插件开发者文档 | 对外自描述在扩，对内自描述在收 |

**一句话总结**：v0.5.0 是一次"产品面大幅扩张（网关、20 工具、Reindex、账号模板）、基础设施层**部分**改动（~~原生层零变化~~ → **Rust 锁与本地存储层实为改动最重的一块**，见下；分层纪律恶化、单测仍不进 CI、仓库无 AI 入口）"的发布。

> **2026-10-19 更正**：此前把 v0.5.0 概括为"原生层零变化"是**错的**。实测 `crates/ragfs/src` 34 文件 / +4481−1083，其中新增 `lock/cache_provder.rs` 1869 行是全仓最大新增文件，`localfs/mod.rs` 重写 819 行。C++ 引擎侧确实未动，但 Rust 侧不是。详见 [`02-Boundaries` 姊妹篇 `architecture/02`](../architecture/02-native-internals.md)。

# 3.1 CI 守卫链：三层语言都进了门，但守卫的密度不同

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 的 CI 由 **30 个 workflow** 组成（`.github/workflows/`；2026-10-19 对 `v0.5.0` 实测：26 → 30，新增 `gateway.yml`/`hermes-plugin-tests.yml`/`host-compat.yml`/`plugin-shared-sync.yml` 等；2026-09-13 曾修正 28 → 26），是一个**按组件拆分的发布流水线矩阵**加上安全扫描与测试网。核对各 workflow 覆盖的语言层后，结论是：三层语言都进了 CI，但密度明显不同。

## 核心矛盾是什么

**单仓多语言的好处是原子性、代价是 CI 复杂度**：Python/Rust/C++ 加上 8 个发布物（主包、3 SDK、CLI、插件、Docker、TOS），每个组件都想有自己的"最小测试集"。OpenViking 用"reusable workflow + 按路径触发"管理这个复杂度——管理得好不好，看原生层有没有被一视同仁。

## 设计判断是什么

### 判断 1：三层语言都进了 CI 门，但**主包单测从未在 CI 运行**——守卫链的最大缺口【硬事实 + 解释】

- PR 检查（`_test_lite.yml`）装 cmake/build-essential（:56-65 三平台），`cargo check -p ragfs-python`（:79）——PyO3 绑定的 Rust 侧在每次 PR 编译检查；多 OS × 多 Python 版本矩阵（:29-45）
- Rust CLI 有专职 workflow（`rust-cli.yml`，musl 交叉编译 cargo-zigbuild + zig，:75-103）
- **但**：出现 pytest 的 workflow 只有 **7 个**（`_test_lite.yml:86-90` cuVS 4 文件；`api_test.yml` / `api_test_effect.yml` 的 `tests/api_test`+`tests/cli`；`oc2ov_test.yml`；`pr.yml` 的 sdk-python / langchain job；`hermes-plugin-tests.yml`；**`gateway.yml:17` `pytest tests/gateway`（v0.5.0 新增）**）——**730 个测试文件（728 个 `test_*.py` + 2 个 `*_test.py`，2026-10-19 实测；旧文写 655）中，`tests/unit/` 与 server/session/storage 等主体测试仍然没有任何 CI 入口**
- `_test_full.yml` 名为 "Test Suite (Full)"，实际只装依赖 + `cargo check` + `build_ext`，**无任何 pytest 步骤**，且全仓无 workflow 调用它（孤儿）——**v0.5.0 仍是孤儿，未被修**。这是本轮同步里"最应该修但 upstream 没修"的一条。
- C++ 层（`src/`）：CI 只编译（为 Python 包 build_ext），无 C++ 专属测试运行；`tests/engine/*.cpp` 存在但 CI 不跑；CodeQL 扫 python+cpp 不含 Rust

评价：修正本篇初稿的判断——问题不是"C++ 密度低于 Rust"，而是**整个主包单测层在 CI 信任模型之外**。CI 实际守护的是：插件（examples）测试 + 集成测试 + 安全扫描 + 发布验证；核心域逻辑（session/memory/storage 的 **730** 个测试文件，旧文写 655）依赖作者自觉与 reviewer 注意力。与 `CONTRIBUTING.md:198` "默认不加新单测" 的测试哲学叠加，机器护栏的缺席被放大了。

### 判断 2：examples/ 插件是 CI 一等公民——"位置是 example，纪律是产品"的又一物证【硬事实】

`pr.yml:21` 起的第一批 job 就是 examples 插件测试：单条 `node --test` 跑约 60 个 `*.test.mjs` 文件（codex-memory-plugin 占 13 个，:33-92），dsh 走 `*.test.mjs` glob 而非 npm test（npm test 用于 openclaw 的 vitest）。结合官方 docs 把这些插件列为主推路径（[integration/01](../../integration/01-start-here.md) 的成熟度表），**examples 目录里的 harness 插件拥有比主包某些子系统更密的 CI**。

评价：这是成熟信号而非混乱——项目清楚自己的实际产品面在哪，并让守卫跟着产品面走，而不是跟着目录名走。

### 判断 3：守卫散落存在，但没有架构守卫脚本【硬事实 + 解释】（初稿判断已修正）

- `ci.yml:28-29`：main 分支 CodeQL security-scan（python+cpp）
- 8 个组件各自的 release workflow（python-sdk / typescript-sdk / rust-cli / dsh-plugin / opencode-plugin / clawhub / controlplane-mcp / langchain）
- **文档一致性守卫现在是三条硬门禁**（v0.5.0 扩了）：`_docs.yml` 依次跑 `npm run test:theme`（:28-30）、**`npm run check:docs` → `docs/scripts/check-docs-consistency.mjs`（双语 + examples 一致性，:32-34）**、`npm run check:api` → `docs/scripts/check-api-reference.mjs`（API 文档 ↔ `server/routers/` 双向校验，:36-38）、**`python3 scripts/check-built-anchors.py`（构建后锚点校验，:46-49）**。旧文"仅此一处"**作废**——现在是**四处**（含 theme 测试）。，其余散落（`.gitattributes` 标记 7 组 sync 生成文件、`.pr_agent.toml` 把真实 bug 编号写成 AI 审查规则）
- `scripts/` 根目录仅 `maintenance/`——无架构守卫链（import 边界、entry-graph 预算之类）

评价：`check-api-reference.mjs` 证明这个团队**会做**机器守卫（双向校验 + 进门禁，质量不输 pi-mono 的 check 链），所以守卫稀疏不是能力问题而是优先级未分配。与判断 1 合并看：CI 信任模型 = 作者自觉 + review + AI 审查代理（.pr_agent.toml），而不是机器门禁。

## 影响是什么

- 贡献者：PR 会自动验证 Rust 绑定编译、cuVS/集成测试、插件测试；但**改 session/memory/storage 的核心域逻辑时，CI 不会帮你跑那 730 个测试文件**（728 个 `test_*.py` + 2 个 `*_test.py`；旧文写 655/653，两口径勿混用）——要自己在本地跑（且 pyproject 的 `--cov` addopts 需要 `uv run pytest --extra test`，见取证报告 A4 的环境矛盾）。
- 对上游：性价比最高的三个补强：① 给 `_test_full.yml` 接上 pytest 并挂进 PR（文件已存在，只差接线——**v0.5.0 依然没接**）；② import-linter 级别的分层守卫；③ CodeQL 补 Rust。

## 最小例证

改动 `crates/ragfs/src/` 一个纯 Rust 文件并破坏编译 → PR 挂在 `cargo check`；改动 `src/abi3_engine_backend.cpp` 引入语义回归（编译通过）→ CI 全绿，只有手动跑 `tests/engine/` 才能暴露。两种结果并存即本文判断。

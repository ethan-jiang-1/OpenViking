# 3.2 贡献门与发布纪律：哲学写在门槛上，发布写成多轨制

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

两份文档值得逐句读：`CONTRIBUTING.md`（v0.5.0 起主文件在根目录，CN/JA 版移入 `docs/repository/`）把**设计哲学写进了贡献门**；`RELEASE.md` 把"发布"定义成**一组相关但独立的资产**而非单一产物。

## 核心矛盾是什么

**接受外部贡献 vs 守住设计一致性**：开源项目要么用流程消化外部 PR（容忍不一致），要么用哲学预筛（提高贡献门槛）。OpenViking 选了后者，而且把哲学写得具体到可执行。

## 设计判断是什么

### 判断 1：CONTRIBUTING 是"core-minimal 纪律"的正式声明，密度罕见【硬事实 + 解释】

`CONTRIBUTING.md`（英文版）的 "What We Value" 一节逐条对应 pi-mono 评价体系里的 core-minimal 纪律：

- "Prefer the smallest complete change. Concise code means fewer concepts, branches, duplicated rules, and speculative abstractions"
- **"Reuse the existing owner of a rule instead of introducing a parallel mechanism"** —— 一条规则一个 owner，正是"极简核"的反面表述
- "Avoid speculative fallbacks, flags, state fields, and abstractions"
- **"Remove code, tests, and compatibility paths that the new implementation replaces"** —— 禁止留兼容尾巴，与 [2.2](../02-Boundaries/2.2_version_contracts.md) 观察到的"无兼容窗口"格式铁律一脉相承
- 明确的 PR 规模优先级："100 行以内的 PR 通常更快被 review；200 行以内优先于更大 PR"（明确声明是优先级不是硬限，且禁止为凑规模省测试）

评价：多数项目的 CONTRIBUTING 停在流程（怎么签 CLA、怎么跑测试），这份把**架构审美**前置到了贡献门。它还有一个值得单独记录的细节：明确声明"无论是否使用 AI 工具，贡献者对变更负责"（"whether or not AI tools were used"）——且 PR 模板有 **Human Involvement 必选字段**（人类参与循环 / 完全 AI 生成，`PULL_REQUEST_TEMPLATE.md:5-8`），哲学落到了表单。三语版本（中/日/英）小节结构 8=8=8 完全对齐，无 DCO/CLA（全仓 grep 零命中）——用 review 纪律替代法律护栏的选择。**v0.5.0 复核**：CN/JA 版被归档到 `docs/repository/`，主 `CONTRIBUTING.md` 涨到 **298 行**，新增了 "Validation and reporting" 安全边界一节（注入/文件访问/租户逃逸要求 trace 真实路径，标题 `CONTRIBUTING.md:197`、内容 `:198-`）——**贡献门在收紧，方向仍然是"把标准写在门槛上"**。

### 判断 1b：测试哲学与守卫缺口互为因果【硬事实 + 解释】

`CONTRIBUTING.md:228`："**Do not add a new unit test or test file by default**"（v0.5.0 行号；建档基线为 :198）——契约测试优先（仓库确有 `test_collector_contracts.py`、`test_retrieval_intent_prompt_contract.py` 等 contract 测试），临时脚本进 `test_scripts/`。skip 纪律总体良好：**18 处** `skipif`（v0.5.0 实测，旧文 19）；但并非零裸跳——另有 **3 处**无条件 `pytest.mark.skip(reason=...)`（v0.5.0 计数同基线）。

评价：这条哲学与 [3.1](3.1_ci_guard_chain.md) 的"主包单测无 CI 入口"合起来形成一个**自洽但高风险的组合**：不鼓励加单测 → 单测不在 CI 焦点上 → **730** 个测试文件（v0.5.0）的实际运行靠自觉。对一个"发布纪律是全仓最强部分"（RELEASE.md 与 workflow 逐条对得上、wheel 发布后做原生 ABI smoke test、Docker digest 校验）的项目，**发布端强、测试端弱**是最准确的画像——它对"发出去的东西打包正确"极其严格，对"没发出去的改动行为正确"相对宽松。

### 判断 2：发布是"多轨制"，版本号空间按消费路径切分【硬事实】

`RELEASE.md` 开篇即定调："OpenViking does not release a single artifact. A release publishes a set of related assets for different usage paths"：

| 发布物 | tag 命名空间 |
|---|---|
| 主包 `openviking` | `vX.Y.Z` |
| Python SDK | `python-sdk@X.Y.Z` |
| TypeScript SDK | `typescript-sdk@X.Y.Z` |
| Rust CLI / npm、ClawHub 插件、controlplane MCP | 各自独立命名空间 |
| Docker / TOS | 与主包同 tag |

"**A formal main-package release should keep the Python package, Docker images, and TOS assets on the same main release tag**"——同一句里同时给出了哪些轨道必须同步、哪些允许独立。

评价：这份文档解释了 [2.2] 遇到的所有版本口径之谜（README "0.3.22" 与 tag v0.4.19 的关系、SDK 独立版本空间）。发布纪律的真实水平：**文档化程度高于大多数单仓多语言项目**（明确到 republishing 路径和验证步骤），且 `RELEASE.md` 自述"based on the tracked GitHub Actions workflows"——发布文档与 workflow 互相引用，不是悬空文档。**但数量要说准**：`RELEASE.md` 实际只点名 **5 个** workflow 文件（`grep -oE "[a-z_-]+\.yml" docs/repository/RELEASE.md | sort -u` → 5），不是 26——26 是 `v0.4.19` 的 workflow 总数，`v0.5.0` 已是 30。

### 判断 3：纪律的盲区在"规则没有机器载体"【解释，引用 3.1】

贡献哲学、review 优先级、发布纪律都文档化了，但 [3.1](3.1_ci_guard_chain.md) 已证：没有架构守卫脚本、没有 AGENTS.md（机器守卫仅一处：`check-api-reference.mjs` 的 API 文档↔路由一致性硬门禁——本篇此前版本写"没有文档一致性检查进 CI"，与 3.1 判断 3 的修正矛盾，2026-09-13 已按 3.1 口径反转）。**纪律目前主要依赖人类 reviewer 的注意力**。CONTRIBUTING 里那句 "whether or not AI tools were used" 恰恰说明作者预期 AI 会参与贡献——但 AI 是最不会自觉读哲学的读者。这个矛盾留给 [4.2](../04-Self-Description/) 展开。

## 影响是什么

- 贡献者：这个项目的 review 文化会系统性地奖励"删代码的 PR"——把改动往"移除兼容路径 + 复用现有 owner"方向整理，比堆功能更容易过门。
- 对上游：CONTRIBUTING 的哲学条目和 RELEASE.md 的多轨制是**可以直接抄走的资产**；缺的只是把哲学脚本化（守卫链）和给 AI 一份入口（AGENTS.md）。

## 源码锚点汇总

- `CONTRIBUTING.md`："What We Value" 五条 + Review Priority（100/200 行）+ AI 责任声明
- `RELEASE.md`："does not release a single artifact" + tag 命名空间表 + 同步约束句
- 交叉：`pyproject.toml:33`（SDK 下限约束）、`_test_lite.yml:79`（cargo check，3.1）

## 最小例证

提两个 PR：一个 +400 行加新功能带 speculative fallback，一个 −150 行删掉重复的校验路径——按文档的 Review Priority 与 What We Value，后者会被更快处理且不违反任何规则。文档的可执行性即本文判断。

# 2.2 版本契约：格式边界有铁律，活接缝没有护栏

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 在**数据格式边界**上有严格的版本契约（ovpack 包格式 v3、ragfs git 索引 v1，均要求精确相等），但在**活的服务接口**（REST/MCP）上没有任何协议版本协商——只有一个装饰性的 URL 前缀 `/api/v1` 和 OpenAPI 里写死的 `"0.1.0"`（`openviking/server/app.py:431`）。而上一篇（[1.1](../01-Architecture/1.1_extension_seams.md)）刚说过：这个服务面恰恰有两条第三方可以插入的暗缝。

## 核心矛盾是什么

**契约成本 vs 演化自由**：协议版本协商（握手、兼容窗口、弃用期）是沉重的承诺；但三方代码（SDK/adapter/插件）与 server 的版本错配又必须有人兜底。OpenViking 的解法是"格式给铁律、接口不设防"——这个组合的自洽性取决于一个前提：**客户端永远和 server 同源同版本**。

## 设计判断是什么

### 判断 1：可携带格式采用"无兼容窗口"铁律【硬事实】

- `openviking/storage/ovpack/format.py:22` `OVPACK_FORMAT_VERSION = 3`
- import 校验是**精确相等**：`ovpack/manifest.py:83-89` `if version_int != OVPACK_FORMAT_VERSION: raise invalid_manifest(f"Unsupported ovpack format_version {version}; this OpenViking requires {OVPACK_FORMAT_VERSION}")`——没有"接受 ≤3"的宽容，没有迁移路径说明
- Rust 侧同哲学但不同力度：`crates/ragfs/src/git/index_store.rs:138` `INDEX_FORMAT_VERSION: u32 = 1`；`:185` mismatch 时是**静默 `Ok(None)`**（按不兼容处理返回空）而非像 ovpack 那样 raise——两处一严一宽，引用时勿混同（2026-09-13 精化：此前版本写"同样精确相等拒绝"）

评价：与 pi-mono protocol v8 的 `isSupportedProtocolVersion` 只接受精确相等**同一个哲学**。在"同一个团队、同仓发布、备份/迁移是运维动作而非第三方生态"的前提下，这是正确的选择——兼容窗口的成本（双写、迁移器、测试矩阵）远大于收益。**但注意这个哲学成立的边界**：一旦 ovpack 成为第三方交换格式（比如社区分享打包的知识库），铁律就会变成"每次升级全体重建"。

### 判断 2：活接口不设协议版本，靠"同源同版"兜底【硬事实 + 解释】

- API 版本化止步于 URL 前缀 `/api/v1`（`server/routers/` 各文件）；FastAPI OpenAPI version 是装饰性的 `"0.1.0"`（`app.py:431`——**它是硬编码字符串，与 `v0.5.0` 这个真实版本毫无关系**，这本身就是"接口层不设防"的最好例证）
- MCP：`/mcp` 端点无自定义版本握手（streamable HTTP 的 MCP 会话层有协议头，但 OpenViking 工具面本身无版本字段；工具 schema 变更 = 破坏性变更）。旧文档曾说工具定义“由服务端集中发布”（`docs/en/agent-integrations/16-capability-reference.md:86` 原文 “These tools are defined on the server side, and future updates will be centrally published there”）——**这句话在 `v0.5.0` 已被删除**，现在该文件 `:81` 换成了 “A server upgrade can add tools without a plugin release; reconnect the client to see them.”。变化的是**措辞**，不是承诺：新版反而更明确地承认“服务端升级可以加工具而插件不必发版”，结论（客户端只能靠重连发现）不变。**引用这句时务必标版本**，别再当现行原文引。
- 为什么能这么干（**初稿判断已修正**）：RELEASE.md 明说 "OpenViking does not release a single artifact"——主包（`vX.Y.Z`）、Python SDK（`python-sdk@X.Y.Z`）、TS SDK（`typescript-sdk@X.Y.Z`）各有**独立 tag 命名空间与发布流水线**。同仓不同版，server 与 SDK 的版本耦合只剩主包对 `openviking-sdk>=0.1.9` 的一行约束（`pyproject.toml:33`）和 `openviking_cli/client/_http_compat.py` 的兼容垫片。即：**发布节奏是"相关但独立"的，接口兼容实际靠的是"约束下限 + 垫片"，而不是版本协商。**

### 判断 3：危险组合——开放接缝 × 无版本契约【硬事实 + 解释，本篇核心】

把 1.1 和本篇合起来看，出现一个结构性风险：

| 接缝 | 第三方可插入 | 有版本契约吗 |
|---|---|---|
| 点分类路径 adapter（`factory.py:29-39`） | ✅ 配置即接 | ❌ `CollectionAdapter` 协议无版本号，接口演进无弃用期 |
| auth 插件（`plugin.py:19`） | ✅（进程内注册） | ❌ 同上，且 `AuthPlugin` 抽象方法签名变更无任何护栏 |
| ovpack / git 索引 | （格式消费者） | ✅ 铁律 |
| REST/MCP 消费面 | ✅（所有用户） | ❌ URL 前缀是唯一"契约"，语义无冻结 |

也就是说：**对 first-party 代码，OpenViking 用铁律保护格式；对第三方代码，OpenViking 什么都不承诺。** 这在今天是自洽的（第三方接入两条暗缝本来就是"未宣传通道"），但如果生态出现——哪怕只是企业内部出现了第二个团队写 adapter——接口漂移会直接砸在他们的 CI 里，且无任何文档告诉他们"哪些接口算稳定面"。

评价：这不是 bug，是**生态优先级的显式低配**。pi-mono 用"无版本契约"评价过同类现象（它的 2.4 篇），OpenViking 的版本略有不同：它的封闭枚举（2.1）反而起到了部分稳定面作用——scope/内容类型/L0L1L2 这些**真正的长期契约**恰好是代码封闭的那几处。即：**模型层稳定（封闭枚举即契约），接口层漂移（活的接缝无契约）**。

## 影响是什么

- 对使用者：生产部署把 server + SDK 锁同一版本（这本来就是官方多 SDK 同源发布暗示的用法）；不要基于 `/api/v1` 的具体端点做旁路集成——它没有任何冻结承诺，`recall` 端点已经被 `@deprecated`（`search.py:548`）演示过一次。
  > ⚠️ **2026-10-19 更正**：本行原文写“**v0.5.0 又演示了第二次**：`POST /api/v1/sessions/{session_id}/used` 直接删除”，**这条时间归因是错的**——该端点是在 **`v0.4.22`** 删除的（commit `676a8954f`，`git tag --contains 676a8954f` 含 `v0.4.22`；`v0.4.19` 的 `server/routers/sessions.py:835` 还有 `@router.post("/{session_id}/used")`）。它比 `v0.5.0` 早两个版本，**不是本轮的破坏性变更**。
  > 同样撤回的还有“`heartbeat` 被删除”这类说法：**`openviking/` 里从来没有过 `heartbeat` 路由**（`git grep -rn heartbeat v0.4.19 -- openviking/` 与当前树均为零命中；该词只出现在 `bot/`、`openviking_gateway/protocols.py:247` 的提示分类关键词里）。**不存在的东西不能被“静默删除”**。
- 对上游：若未来想认真做第三方 adapter 生态，第一件事不是文档化点分类路径，而是给 `CollectionAdapter`/`AuthPlugin` 加接口版本或从 `CollectionAdapter.protocol_version()` 起步——那时候本文的判断可被检验。

## 源码锚点汇总

- `ovpack/format.py:22` / `ovpack/manifest.py:83-89`（铁律 + 原话）
- `crates/ragfs/src/git/index_store.rs:138, 185`
- `app.py:431` / `server/routers/`（`/api/v1` 前缀）/ `search.py:548`（`@router.post("/recall", deprecated=True)` 弃用实例）
- 对照：`factory.py:29-39`、`plugin.py:19`（1.1 的两条无契约接缝）

## 最小例证

用旧版本号（`format_version: 2`）构造一个 ovpack manifest 调 import——得到的是"requires 3"硬错误而非降级迁移；同一天把某个 `/api/v1` 响应字段改名，三个 SDK 与 server 一起发版后无人报错。两种行为并存即本文判断：格式有铁律，接口靠同源。

**结论修正程度**：判断 2（活接口不设防）从“观察到的风险”升级为**“已被多次兑现的风险”**；判断 3 的表格不需要改，但它预测的“接口漂移会砸在第三方 CI 里”在**本轮（v0.5.0）只兑现了一次**（MCP 工具面 15→20 的纯增量），**不是两次**。`/used` 的删除是 `v0.4.22` 的旧账（见上），`heartbeat` 则从未存在——原文把两者都算进“这一轮”，是把“旧账”与“不存在”一起当成了证据。
> **这条更正本身就是判断 2 的又一个例证**：连本套文档都曾把两件并不发生在该版本的事写成“实打实发生了两次”。

**一个反向的正面信号**：ovpack v3 与 `INDEX_FORMAT_VERSION = 1` **都没动**。从 v0.4.19 到 v0.5.0 这一轮迭代下来，格式铁律守住了——"格式给铁律、接口不设防"这个组合在实测中不是口头承诺。

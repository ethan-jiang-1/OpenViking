# 2.1 封闭枚举：四处"改不了"的设计，各自的理由是否成立

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 的核心模型里有四处枚举是**代码封闭**的：URI scope 白名单、内容类型映射、上下文层级（L0/L1/L2）、记忆合并操作。核对每一处的封闭机制与护栏后，发现它们的封闭质量参差。

## 核心矛盾是什么

**封闭枚举是不变量的守护者**（加了 L3、加了新 scope，检索/加载/ACL 的全部组合假设都要重验），但**封闭同时堵死了演化通道**——社区无法试验"第四种上下文"。矛盾在于：哪些封闭是对的（语义核心）、哪些封闭只是"还没想清楚开放协议"的偷懒？

## 设计判断是什么

### 判断 1：URI scope 封闭得最严密，且有 fail-closed 护栏【硬事实 + 解释】

- 白名单四组常量：`openviking_cli/utils/uri.py:58-71`（LISTABLE/LEGACY/INTERNAL/ALIAS）
- 请求边界校验抛 `InvalidURIError`（`core/uri_validation.py:52-62`）；canonical 解析对 `~`/`session` 别名 **fail-closed**（`namespace.py:244-251`）
- `upload` scope 一律拒绝访问（`namespace.py:334-335`）——内部 scope 不因"能写"而变得可读

评价：**这是全部四处里质量最高的封闭**。scope 是 ACL、存储布局、内容类型三套机制的联合键，封闭正确。护栏到位（别名只在请求边界展开、内部 scope 不可读、保留段报错 `:302-316`），符合"枚举即安全边界"的标准。

### 判断 2：内容类型映射封闭，但封闭点选得聪明【硬事实 + 解释】

`core/namespace.py:14-17` `_CONTENT_TYPES_BY_SCOPE`：`user` scope 下三种（`memories→memory`、`resources→resource`、`skills→skill`），**`agent` scope 下只有一种**（`skills→skill`，`:16`）。加"第四种内容类型"需要同时改：这个映射、存储 schema、记忆抽取的 memory_type 过滤（`MemoryOperationSkipCode.memory_type_filtered`，`memory/dataclass.py:173`）、MCP 工具的 delete 类型边界（capability-reference §3.5）——**四处联动，代码封闭客观上阻止了半成品类型进入**。

评价：封闭理由成立，但四处联动的成本没有被文档化（没有"如何新增内容类型"的内部指南），意味着连 first-party 的演化都靠口口相传。

### 判断 3：L0/L1/L2 是最值得商榷的封闭【硬事实 + 解释】

`core/context.py:34-39` `ContextLevel` 三值枚举（ABSTRACT=0 / OVERVIEW=1 / DETAIL=2），物理上贯穿：向量记录的 `level` 字段、**索引层 push-down 过滤**（`viking_vector_index_backend.py:2988-2989` `In("level", level)`——v0.5.0 起这是唯一生效的过滤点，旧文写的 `hierarchical_retriever.py:301-307` 是已删除的递归骨架）、`LEVEL_URI_SUFFIX = {0: ".abstract.md", 1: ".overview.md"}`（`hierarchical_retriever.py:56`，唯一使用点 `:372`）、sidecar 写入（`abstract_overview.py:533` `write_abstract_overview`）。加 L3（比如"跨目录主题摘要"）需要动全部四处 + RFC 的 OKF 元数据语义。

评价：**短期封闭正确**（L0/L1/L2 的语义分工——相关性判断/规划/全文——覆盖了加载决策的完整空间，pi 的 L0/L1 RFC 也是三层封顶）；但 freshness 父冒泡机制（`plan_abstract_overview_refresh()`，`abstract_overview.py:671`）已经在层间引入了时间维度——**下一个演化轴（新鲜度/版本）正在从枚举的缝隙里长出来**，未来大概率以 metadata 字段而非新层级的形式落地。这不是批评，是对演化方向的预测，可被证伪。

### 判断 4：合并策略是"prompt 封闭"，与其他三处性质不同【硬事实 + 解释】

`memory/merge_policy.py:5-19` `MEMORY_MERGE_POLICY` 是注入 LLM prompt 的常量文案（"同 identity 才可 merge；不确定就保持独立"），不是配置项。对比 `MergeOp`（PATCH/REPLACE/SUM/IMMUTABLE 四值，`merge_op/base.py:121-127`）是按 schema 字段定义的、数据驱动的。

评价：**用 prompt 而非代码封闭策略**是这套设计里最脆弱也最务实的一处——脆弱在于策略没有测试护栏（改文案 = 改行为，无 CI 能发现）；务实在于抽取策略本质是 LLM 行为调参，代码封闭反而假。这是四处封闭里唯一"护栏缺席"的。

## 影响是什么

- 四处封闭中三处（scope/类型/层级）封闭质量高，说明**核心模型的不变量意识很好**；
- 唯一的系统风险在合并策略的 prompt 封闭：任何想稳定复现记忆行为的产品集成，都必须冻结整个 OpenViking 版本，而不是只冻结配置。
- 判断 3 的演化预测（时间轴从 metadata 长出）可作为后续轮次的验证点：若后续版本出现 freshness 相关的新枚举或新 sidecar，本条即被证实。
- **v0.5.0 部分证实（2026-10-19）**：`ContextLevel` 仍然是三值（`core/context.py:34-39` 未变），**没有出现 L3**；但时间/新鲜度确实以 **metadata 字段**的形式扩了——`_METADATA_ORDER`（`abstract_overview.py:31`）与 `EMBEDDING_METADATA_FIELDS = ("directory",)`（`abstract_overview.py:30`）把"可变 metadata"从 embedding 输入里排除。方向与预测一致：**不新增层级，而是给层级加旁路字段**。

## 源码锚点汇总

- `uri.py:58-71` / `uri_validation.py:52-62` / `namespace.py:244-251, 302-316, 334-335`
- `namespace.py:14-20` / `memory/dataclass.py:173`
- `context.py:34-39` / `abstract_overview.py:30-31, 533, 671` / `viking_vector_index_backend.py:2988-2989` / `hierarchical_retriever.py:56, 372`
- `merge_policy.py:5-19` / `merge_op/base.py:121-126`

## 最小例证

向 server 发一个 `viking://database/mydb` 的写请求——`InvalidURIError` 且报错文案只列出白名单 scope（`uri_validation.py:54-62`），不会把"未注册"误报为"不存在"。行为即证据：scope 是安全枚举，不是目录约定。

## 状态标注

- 硬事实：四处封闭的机制与锚点（2026-10-19 对 `v0.5.0` 复核）
- 反转记录（2026-10-19，v0.5.0）：**枚举本身一个没变**（scope 白名单、内容类型映射、L0/L1/L2、MergeOp 四值全部保持）；变的只是消费点——`LEVEL_URI_SUFFIX` 迁到 `hierarchical_retriever.py:56`，层级过滤下沉到索引层 `In("level")`。scope 白名单仍与 v0.4.19 **逐字节相同**

## v0.5.0 复核小结（2026-10-19）

四处封闭枚举**逐条核实，结论全部成立**，只有一处口径写粗了：

| 判断 | 复核 | 说明 |
|---|---|---|
| 1. URI scope 最严密 | ✅ | `uri.py:58-71` 四组常量未变（LISTABLE/PUBLIC/LEGACY/INTERNAL/ALIAS，另有 VISITABLE 并集） |
| 2. 内容类型映射封闭 | ✅ | `_CONTENT_TYPES_BY_SCOPE` 仍在 `namespace.py:14-17`；**原句"只在 user/agent scope 下生效"写得太笼统**——实际 `agent` scope 只映射 `skills`，不比 `user` 全 |
| 3. L0/L1/L2 最值得商榷 | ✅ | `ContextLevel` `context.py:34-39` 三值；索引层 push-down `viking_vector_index_backend.py:2988-2989`（注意该文件在 `openviking/storage/` 下，不在 `vectordb/collection/`）；`LEVEL_URI_SUFFIX` `hierarchical_retriever.py:56`、唯一使用点 `:372`；`plan_abstract_overview_refresh` `abstract_overview.py:671` |
| 4. 合并策略是 prompt 封闭 | ✅ | `MergeOp` 四值仍在 `merge_op/base.py:121-127`；`merge_policy.py` 仍是常量文案、无测试护栏 |

**"下一个演化轴从枚举缝隙里长出来"这个预测，v0.5.0 给了半个证据**：`freshness` 父冒泡（`abstract_overview.py:671`）确实还在，而且**没有**变成 L3——它仍然是 metadata 机制。预测方向对，兑现形式也对。

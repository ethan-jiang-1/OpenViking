# 1.2 分层纪律：名义分层在依赖图上破了两处

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 的包结构暗示一条清晰的单向分层：`core`（域模型）← `storage`（存储）← `service`（编排）← `server`（接口）。但沿 import 方向抽查后，依赖图实际破了**两处**——而且破的位置都很有信息量。

> **2026-10-19（v0.5.0）复核：两处都还在，且规模更大。** 反向 import `openviking_cli` 的文件从 282 涨到 **319**（共 **22 个子目录**，前几位：storage 66 / server 42 / session 38 / parse 37 / models 24 / service 20 / utils 16 / config 13 / eval 12 / retrieve 10 / core 6…；原句只列了 9 个目录共 259 个，容易误读成合计）。upstream 没有做这一层的清理，这一轮的架构变化全部发生在别处（网关、队列、检索）。

## 核心矛盾是什么

**包的命名 vs 包的实际角色**：当"CLI 包"实际承担共享内核（shared kernel）、"存储层"实际承担任务编排时，import 方向只是如实记录了角色的错位。问题不在纪律松懈，在于**命名没有跟上真实结构**。

## 设计判断是什么

### 判断 1：core 是"域模型"，但它的基本类型住在 CLI 包里【硬事实】

`openviking/core/` 多个最基础的模块反向 import `openviking_cli`（CLI 包）：

| core 文件 | 从 openviking_cli 拿什么 | 锚点 |
|---|---|---|
| `core/context.py` | `UserIdentifier`、`VikingURI` | `:12-13` |
| `core/namespace.py` | 同上 | `:11-12` |
| `core/uri_validation.py` | `InvalidURIError`、`PermissionDeniedError`、`VikingURI` | `:14-15` |
| `core/retrieval_targets.py` | `ContextType`（`from openviking_cli.retrieve import`）+ `InvalidArgumentError`/`PermissionDeniedError` | `:16-17` |
| `core/path_variables.py` | `get_logger` | `:14` |
| `core/directories.py` | `NotFoundError`（另有函数内延迟 import `get_logger`） | `:30`、`:342` |

这不是孤例而是**系统性的**：URI 校验、异常类型、用户标识、内容类型——core 的地基材料全在 `openviking_cli` 包里。加上此前已确认的 client 兼容链也住在那里（[`integration/01`](../../integration/01-start-here.md) 误解点 1），**`openviking_cli` 实际是 wearing CLI 外衣的共享内核**。

评价：这是多仓历史演化留下的接缝（CLI 包可能先于 core 存在）。规模经全量核验（`v0.5.0`）：**319 个文件反向 import `openviking_cli`**（含 `openviking/__init__.py` 本身；分布在 **22 个子目录**，见上——2026-10-19 实测；建档基线 `0f77ab56` 为 282）。加上此前确认的 client 兼容链也住在那里（[`integration/01`](../../integration/01-start-here.md) 误解点 1），**`openviking_cli` 实际是 wearing CLI 外衣的共享内核**。危害有限（同仓发布，无独立版本契约），但两条真实代价已经发生：① 依赖方向语义混乱——"CLI" 包在 server 部署里也是运行时必需；② **想抽出一个"纯 core"分发包的人会发现 core 抽不出来**——它抓着 CLI 包不放。deletion test 式的问法：把 `openviking_cli` 删掉，`core` 站得住吗？答案是否。

### 判断 1b：连"请求身份"类型都住在 server 包里【硬事实】

更极端的散落证据：`RequestContext` / `Role`——几乎所有层都要用的请求身份类型——定义在 **server 包**（`openviking/server/identity.py`），被 storage 层模块级 import（`storage/viking_vector_index_backend.py:19`、`storage/collection_schemas.py:21`，全量核验约 26 个 storage 文件），**连 core 自己也 import 它**：`core/retrieval_targets.py:14`、`core/namespace.py:10`、`core/directories.py:21`。也就是说基础类型的真实分布是：URI/异常在 CLI 包、请求身份在 server 包、ContextLevel 在 core 包——**没有一个"地基包"，地基散落在三个包里**。

### 判断 2：storage 的 QueueFS 处理器向上抓 service 层，且 service↔server 双向【硬事实 + 解释】

名义上 service 依赖 storage；但反向边不止一条（全量核验见取证报告 §3）：

- **storage→service：`v0.5.0` 实测 11 个文件**（基线 8 个），**其中 8 个在 `queuefs/`**：`semantic_processor.py:38-40`、`semantic_executor.py:16-18`（替代已删除的 `semantic_dag.py`）、`add_resource_processor.py:13-14`、`session_commit_processor.py:13-14`、`external_task_processor.py:10-11`、`reindex_processor.py:11-12`、`semantic_work.py:11`、`queue_manager.py:15`；`queuefs/named_queue.py` 的 service import 已清零。**另有 3 个不在 queuefs**：`collection_schemas.py:23`、`viking_vector_index_backend.py:22`、`viking_fs/_snapshot.py:541,833,871`（函数内延迟 import）。三者 import 的全是 `service/task_tracker*`、`task_work_index`、`task_tracker_concurrency` 这类**任务编排辅助**，不是 `SessionService` 之类的业务服务——`session_commit_processor.py:22` 那处延迟 import `SessionService` 才是真正导入业务服务。
- **storage→server：`v0.5.0` 实测 29 个文件**（基线 26；此前版本写"2 处"只数了显式列举的两个，系误计）——多为 `server.identity` 的 RequestContext/Role 与 `server.error_mapping`
- **service↔server 双向**：正常方向 server→service 为 **11 个文件**；反方向 service→server **`v0.5.0` 实测 17 个文件**（基线 15），如 `service/core.py:17-21,613`、`service/session_service.py:15-16` 反向 import `server.identity`/`server.config`/`server.account_settings`

对比同目录对 core 的依赖全是干净向下（`storage → core` 的 import 均符合名义分层，抽查 `collection_schemas.py:19`、`acl.py:9-10` 等）。

评价：破口的形状有规律——storage 的破口**全部集中在 QueueFS 异步处理器与身份类型**：前者因为"任务"抽象（task tracker / task work index）被放进 service 层，后台处理器不得不用；后者因为 `RequestContext`/`Role` 放错了包。**（2026-09-13 修正：此前版本写"唯一干净的方向是 core 不 import service/server"——经复核不成立**：core 有 3 处 `from openviking.server.identity import RequestContext`（`core/retrieval_targets.py:14`、`core/namespace.py:10`、`core/directories.py:21`，即判断 1b 的证据）。准确说法是：**core 对 service/server 只有一类依赖（identity 类型），且无 service 业务逻辑依赖——是"最薄"的方向，不是"零依赖"方向**。名义四层里没有一条方向完全干净。）

### 判断 3：越层是"延迟 import 习惯"缓解的，这既是优点也是症状【硬事实 + 解释】

大量 storage→service 的 import 写在函数体内（`_snapshot.py:490` 等）——这是打破循环依赖的惯用手法。优点：模块加载图无环，server 启动不受影响；症状：**依赖被藏进了函数体，grep 顶层 import 看不出真实依赖图**（本篇的表就是逐文件搜函数体才拼全的）。没有 import-linter 之类的机器守卫（[3.1](../03-Discipline/3.1_ci_guard_chain.md)），分层约束的执行完全依赖这个"藏"字诀不扩散。

## 影响是什么

- 对使用者/集成者：无直接影响——同仓发布掩盖了一切。
- 对上游：如果未来拆包（比如把 core 作为独立库发布给"只想嵌入 viking:// 文件系统"的用户），**第一个工程障碍就是这两处反向边**。把 `VikingURI`/异常体系搬进 core、把 task 抽象下沉为独立模块，是拆包前的两笔必还的债。

## 源码锚点汇总

- core→CLI：`core/context.py:12-13`、`core/namespace.py:11-12`、`core/uri_validation.py:14-15`、`core/retrieval_targets.py:16-17`、`core/path_variables.py:14`、`core/directories.py:30,342`
- core→server（identity 类型）：`core/retrieval_targets.py:14`、`core/namespace.py:10`、`core/directories.py:21`

- 干净对照：`storage/collection_schemas.py:19`、`storage/acl.py:9-10`、`storage/viking_fs/_ops.py:11-12`（storage→core 全部合规）
- 全量核验底账：[`../../_notes/seams-boundaries-evidence.md`](../../_notes/seams-boundaries-evidence.md) §3

## 最小例证

在只有 `openviking` 主包、没有 `openviking_cli` 的环境里 `import openviking.core.namespace`——直接 ImportError。core 的第一行依赖就穿过了 CLI 包，即判断 1 的物理证明。

## 状态标注（含 v0.5.0 复核结论）

- 反转记录（2026-10-19，v0.5.0）：本节下方的复核结论逐条给出；结论是**本文判断全部仍然成立**，但规模/数字有更新，详见复核表

两处破口**都还在，而且都变宽了**。全部按 `v0.5.0` 重新数过：

| 越层方向 | 基线 `0f77ab56` | `v0.5.0` | 说明 |
|---|---|---|---|
| 反向 import `openviking_cli` | 282 文件 | **319 文件** | 分布在 22 个子目录 |
| storage→service | 8 文件（全在 queuefs） | **11 文件**（8 queuefs + 3 非 queuefs） | 新增 `reindex_processor`、`semantic_work`、`collection_schemas`、`viking_vector_index_backend` |
| storage→server | 26 文件 | **29 文件** | |
| service→server（反向） | 15 文件 | **17 文件** | 正常方向 server→service 仅 11 文件 |
| core→`openviking_cli` | 6 文件 | **6 文件** | 位置未动——地基依然抓着 CLI 包 |

**这一轮修正了三个数**：原文档写的 storage→service「仍是 6 个文件」、storage→server「约 26」、service→server「15」**全部是基线值没重算**——真实值是 11 / 29 / 17。这是同步轮最典型的偷懒：只重算了最显眼的那个数（282→319），其余照抄。

**一个被找回的细节**：storage→service 的 11 个文件里，只有 `session_commit_processor.py:22` 一处真的导入了业务服务（`SessionService`，且是函数内延迟 import）；其余十处导入的都是 `service/` 下的**任务编排辅助**（`task_tracker`、`task_work_index`、`task_tracker_concurrency`）。这削弱了"storage 直接调业务服务"的措辞强度，但**不改变越层事实**——`service/` 是名义上的上层，storage 从它那里拿实现细节，方向仍然是反的。

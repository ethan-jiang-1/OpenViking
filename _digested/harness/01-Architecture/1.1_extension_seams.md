# 1.1 扩展接缝：三个注册点，两种哲学

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

OpenViking 有三个明确的扩展接缝：**向量后端 adapter**、**认证插件**、**MCP 工具面**。逐一核对注册机制后发现，它们的"可扩展程度"并不一致，而且没有一篇文档把三者放在一起说清楚。

> **2026-10-19 复核修正（口径）**：原文这里写的是"**内容解析**（parse/ingest）"，但正文三个判断实际写的是 **MCP 工具面**——**导语与正文列举的接缝对不上，导语错了**。内容解析确实有注册机制（`openviking/parse/parsers/registry.py:51-69`，10 个 parser），但它是[`1.3` 的判断 3](../01-Architecture/1.3_data_seams.md)，归在 1.3 而不是本篇。本篇的第三根柱子是**接缝不存在**这个结论（MCP 工具面没有第三方扩展点），这本身也是接缝评价的一部分。

## 核心矛盾是什么

**接缝的开放性 vs 发现机制的成本**：提供扩展点（抽象类 + 注册表）是廉价的；让第三方代码**被自动发现并加载**是昂贵的（entry-points、插件市场、版本兼容矩阵）。OpenViking 在不同接缝上选择了不同的妥协点，但未显式声明这个差异。

## 设计判断是什么

### 判断 1：向量后端接缝是"真开放"——配置即扩展【硬事实 + 解释】

`openviking/storage/vectordb_adapters/factory.py`：`_ADAPTER_REGISTRY` 是硬编码 **6 项**白名单（local/cuvs/http/volcengine/vikingdb/**opengauss**，`:16-23`），**但** `:31-42` 有动态加载路径——backend 配置含 `.` 时按 `module.Class` 路径 import，接受任何 `CollectionAdapter` 子类（`:37` issubclass 校验）；`:44-48` 失败则落到白名单报错。

**这意味着第三方不需要 fork 源码、不需要注册调用**：自己写一个 adapter 包 + 在 `storage.vectordb.backend` 配置里写点分类路径，就能接入。这是一条**功能完整但零宣传的扩展通道**——源码内没有任何文档提及（错误消息 `:44-48` 只列白名单 6 项，会让人以为没有别的可能）。

评价：机制优雅（iseu 校验兜底 + 统一 `from_config` 构造协议），但**可发现性为负**——错误消息主动误导。这是"接缝存在"与"生态可形成"之间的差距。

### 判断 2：认证插件接缝是"半开放"——有注册表，无发现机制【硬事实】

`openviking/server/auth/plugin.py:19` `AuthPlugin` 抽象基类设计完整（`resolve_identity`/`validate_config`/`initialize`/`shutdown` 生命周期齐全，docstring 明说 "Third-party plugins subclass this and register via `@register_auth_plugin`"，`:22-24`）；注册表 `auth/registry.py:27` 支持装饰器与编程式注册，按 `auth_mode` 字符串查表、重复注册报错（:49-51）。

**但**：全仓 grep 无 entry-points（`pyproject.toml` 零声明，v0.5.0 复核仍为零）；内置 5 个插件的注册方式是 `plugins/__init__.py` 的**直接 import + 模块级 register 调用**。第三方插件要生效，必须在自己的启动器里先 import 再注册——server 本身不会发现它。

评价：这是"库式扩展"而非"产品式扩展"——对上游（volcengine 自己加 oidc/ldap）够用，对外部贡献者等于要写一个 fork 的启动脚本。与判断 1 对照，**同一个产品里两种扩展哲学并存**，且没有文档解释为什么。

### 判断 3：MCP 工具面是"server 单极"【硬事实 + 解释】

**20 个**工具全部以 `@mcp.tool` 定义在 `openviking/server/mcp_endpoint.py`（见 [`integration/01`](../../integration/01-start-here.md)）。第三方**没有**在 server 端追加工具的接缝——工具面随 server 版本走。这是刻意收拢（工具面统一 = 所有透传 harness 行为一致），代价是 server 端没有插件生态的位置。

> **v0.5.0 修正两处**：① 工具数 15→20；② **官方不再是"集中发布而不重装插件"的口径**——`16-capability-reference.md:81` 现在写 "A server upgrade can add tools without a plugin release; reconnect the client to see them"。**这是判断 3 的一次自证**：工具面确实是 server 单极，所以加工具客户端零成本；但也确实没有任何客户端可控的版本信号，只能靠重连。结合 pi-mono 的对照：pi 把工具注册做成宿主侧扩展点（`ExtensionAPI` 的 tool 注册），OpenViking 把它做成 server 的私有面——**工具生态的位置一个在宿主、一个在 server，各自与产品语义自洽**。

## 影响是什么

- 对使用者：今天想换向量后端，**别等官方适配**——点分类路径已经能用（先读 `CollectionAdapter.from_config` 协议）；想加自定义认证，评估一下"维护 fork 启动器"的成本。
- 对上游：接缝不均衡 + 不可发现，意味着外部生态大概率不会在 adapter/auth 两点形成，能力增长将主要靠 first-party。这不是缺陷而是选择，但**选择未被记录**——本文即记录。

## 源码锚点汇总

- `factory.py:16-23`（白名单 6 项）/ `:31-42`（动态加载暗门）/ `:44-48`（误导性错误消息）
- `plugin.py:19-28`（抽象基类 + 第三方注册声明）/ `registry.py`（注册表）/ `plugins/__init__.py`（内置直注册）
- `mcp_endpoint.py:5-7`（工具面集中定义自述）、`:298-352`（统一错误包装）

## 最小例证

把 `storage.vectordb.backend` 配置改成 `"my_pkg.adapters.MyAdapter"`（任意实现了 `CollectionAdapter` 的类路径），server 能启动并在错误配置时得到白名单报错而非"不支持点分类路径"——两种行为并存即是本文判断的物理证明。

## 状态标注

- 反转记录（2026-10-19，v0.5.0）：**三个接缝的哲学一个没变**——adapter 仍是配置即扩展（白名单 5→6，加了 opengauss）、auth 仍是有注册表无发现机制、MCP 仍是 server 单极（15→20 工具）。变的是官方对第三种的说法：从"集中发布"改成"重连即见"，等于承认工具面没有版本信号

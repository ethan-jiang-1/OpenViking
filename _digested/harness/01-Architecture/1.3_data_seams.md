# 1.3 数据接缝：provider 宽、ingest 中、parse 窄——开放度与产品距离成反比

> **基线**：`v0.5.0`（2026-10-19 全文复核；建档基线 `0f77ab56`）。

## 现象是什么

数据进入 OpenViking 有三道接缝：**模型 provider**（embedding/VLM，语义加工的原材料）、**ingest source**（外部 harness 的日志源适配器）、**parser**（文件类型解析）。逐一核对注册机制后发现，三者的开放度恰好排成一列，且方向出人意料。

## 核心矛盾是什么

**开放谁，取决于"第三方想改什么"的假设**。OpenViking 假设第三方想换模型、想接入自己的 harness 日志（用户侧诉求），而不太想写文件解析器（管线内部组件）——于是前者宽、后者窄。这个假设对不对，决定这套接缝的评价。

## 设计判断是什么

### 判断 1：provider 接缝是最宽的一层——配置即换，含无云端点【硬事实】

- Embedder：抽象基类 `models/embedder/base.py:248` `EmbedderBase(ABC)`（`embed/embed_query/embed_async` 全异步对称 API），工厂为配置驱动的 `factory_registry` **13 选 1**（`openviking_cli/utils/config/embedding_config.py:167-181` `_VALID_PROVIDERS`；默认 volcengine；校验 `:210-214`）：openai、**azure**、gemini、jina、voyage、cohere、dashscope、minimax、vikingdb、volcengine、**ollama**、**litellm**（通用 OpenAI 兼容代理——等于任意 OpenAI 兼容端点可配）、**local**（本地嵌入，无云端路径；原设计稿 `docs/design/local-embedding-llama-cpp-design.md` **已在 v0.5.0 随 `docs/design/` 整目录删除**，现只能读代码 `models/embedder/local_embedders.py`）（2026-09-13 修正：此前版本写"12 选 1"漏了 azure/ollama，且锚点 :1011/:1046-1063 指向 get_embedder/failover 辅助函数而非注册表定义处）
- VLM：`models/vlm/base.py:64` `VLMBase(ABC)` + `:342` `VLMFactory` 工厂 + 两个包装器：`FailoverVLM`（:413，故障切换）与 `MultiCredentialVLM`（:766，多凭证轮换）；provider 白名单 `models/vlm/registry.py:10-18` `VALID_PROVIDERS` **7 个**（volcengine/openai/azure/kimi/glm/litellm/openai-codex——v0.5.0 复核未变），`VLMConfig` 支持多 provider + `api_base` + failover（`vlm_config.py:141-155`）
- 配置面：`open_viking_config.py:181,185` `embedding: EmbeddingConfig` / `vlm: VLMConfig` 一等字段；另有独立 `compile_api.base_url`（:142，校验必须带 scheme :150-151）——OpenAI 兼容端点直接可配；docstring 明示接法（`embedding_config.py:78-88`）

评价：与 [1.1](1.1_extension_seams.md) 的 adapter/auth 形成鲜明对比——**模型层不需要任何"接缝机制"，配置本身就是接缝**。litellm + local 两个选项的存在，说明设计者明确考虑了"非 volcengine 用户"和"无云用户"。精确表述其开放边界（取证报告 §2）：**端点开放（任意 OpenAI 兼容 base_url 可配）、provider 代码集合封闭**（新增 provider 类需改内核工厂表）——对使用者是宽门，对 contributor 是窄门。这是全仓最健康的接缝：宽、可发现（config schema 自描述）、无需 fork。

### 判断 2：ingest source 接缝是"设计过的插件点"——公开装饰器 + 自由配置键【硬事实】

`openviking/ingest/registry.py` 的设计意图写在模块 docstring 里（:4-6）：

> "Adding a harness = one `@register_source("name")` decorator on a `LogSource` subclass; **no config-schema change is needed (config keys are free-form)**"

- 公开类装饰器 `register_source`（:14-24，`SOURCE_REGISTRY` 字典，重名覆盖仅 warning 不报错）
- 配置键自由形态：`iter_enabled_sources`（:39-56）直接把 free-form 的 `IngestHarnessConfig` 透传给 source 构造器——**新增数据源不需要动配置 schema**
- 内置 **8 个** harness 适配器（v0.5.0：6 → 8）：claude_code（`:35`）、codex（`:59`）、cursor（`:27`）、hermes（`:23`）、**mimo（`mimo.py:48`，新增）**、openclaw（`:40`）、opencode（`:25`）、**workbuddy（`workbuddy.py:121`，新增）**——OpenViking 明确把"吃别家 coding agent 的会话日志"当产品能力，且这条接缝是本轮**唯一真的长出新适配器的扩展点**

评价：这是三个接缝里**唯一公开声明"如何加一个新的"**的（docstring 即教程）。局限与 auth 插件相同：进程内注册、无 entry-points（[1.1](1.1_extension_seams.md) 判断 2 的模式复现），第三方用它的前提是自己写启动器。重名覆盖用 warning 而非 auth registry 的 ValueError（`auth/registry.py:49-51`）——同类机制两处不一致，小瑕疵。

### 判断 3：parse 是两级结构，窄门里藏着一扇中门【硬事实 + 解释】

parse 实际有两级接缝，开放度不同：

- **来源层（accessor）**：`parse/accessors/registry.py` 注册 5 个数据源 accessor（git/web-feed/http/feishu/local，`_register_defaults` `:53-93`），有**公开的 `register()`** 且按 priority 排序（`:95-113`）——与 auth 同款"进程内编程式注册"，但 API 是公开的。**v0.5.0 复核：5 个 accessor 未变，逐个确认仍在 `:53-93` 内 import + register**
- **文件类型层（parser）**：`parse/registry.py:29` `ParserRegistry` 单例，`__init__` 硬编码注册 10 个 parser（text/markdown/pdf/html/anydoc/zip/directory/image/audio/video，:51-69；2026-09-13 修正：此前版本写 11 个，实数 10 个 `_register` 调用），`_register` **私有**（:71），分发按扩展名 map（`get_parser_for_file` :78-101）；`BaseParser` ABC 在 `parsers/base_parser.py:11`。可配置的部分只有每个内置 parser 的**参数**（`parser_configs`），不是 parser 类型本身——**第三方加新文件类型 = fork，无 entry-point、无配置注入**（取证报告 §1 硬事实）
- 另有一条外部解析旁路：`ParserRouter`（`parser_router.py:47-85`）按 `parser_api.enable` + 扩展名白名单把请求路由到外部 UnderstandingAPI（host 固定拼 `/api/v3`，Ark 风格，`understanding_api.py:67-69`）——解析能力可以外包给云，但"加一类文件"仍然不开放

评价：窄得有道理——parser 深耕管线内部（依赖 understanding API、媒体探测），第三方自写 parser 的质量风险与换模型不可同日而语。但不对称值得指出：**任何"新文件类型"需求都被堵在 fork 上**（notion 导出、专属二进制格式正是企业集成常见诉求），而 accessor 层已经示范了正确的开放姿势（公开 register + priority）。把 `_register` 提升为公开方法、复用 accessor 的模式，是极低成本的开放——现状像是"还没轮到"而非"刻意封死"。

## 影响是什么

- 对使用者：换模型别 fork——`EmbeddingConfig`/`VLMConfig` 是正路，litellm 兜底几乎覆盖一切 OpenAI 兼容端点；接自家 agent 日志用 `@register_source`（接受"自写启动器"成本）；新文件类型目前只能等官方或 fork。
- 三档开放度的排序本身是可复用的评价结论：**离用户数据越近的接缝越开放（provider），离管线核心越近的越封闭（parser）**——与 [2.1](../02-Boundaries/2.1_closed_enums.md) 的"模型层稳定、接口层漂移"互为镜像。

- `parse/registry.py:29,51-69,71-76,78`（单例 + 私有注册 + 扩展名分发）

## 最小例证

三个"加一个新 X"的操作路径对比：新模型 = 改配置文件即可（零代码）；新日志源 = 一个装饰器 + 启动器 import（两行代码）；新文件类型 = 改 `ParserRegistry.__init__`（fork）。三条路径的代码量梯度即本文判断。

## 状态标注

- 反转记录（2026-10-19，v0.5.0）：三档开放度排序**完全没变**（provider 宽 > ingest 中 > parse 窄）。唯一实质变化是 ingest 档真的长出了两个新适配器（mimo、workbuddy，6→8），实证了「公开装饰器 + free-form 配置键」这条设计确实降低了接入成本；provider 档 13 选 1 与 VLM 7 个都没变；parse 档仍是 10 个硬编码 parser + 私有 `_register`

## v0.5.0 复核小结（2026-10-19）

本文三个判断在 v0.5.0 的复核结果：

| 判断 | 结论 | 变化 |
|---|---|---|
| 1. provider 接缝最宽 | ✅ 成立 | embedding provider 13 未变；vectordb adapter 白名单 **5 → 6**（+opengauss）；VLM 7 未变 |
| 2. ingest source 是设计过的插件点 | ✅ 成立，且更强 | **6 → 8** 个 source（新增 `mimo`、`workbuddy`），是本轮唯一真的长出新适配器的扩展点 |
| 3. parse 两级结构、窄门藏中门 | ✅ 成立 | parser 仍 10 个（`parse/registry.py` 的 `_register` 调用逐个数过）、accessor 仍 5 个、`_register` 仍是私有 |

**口径修正一处**：判断 3 里的 `parse/registry.py:51-69` 路径写对了，但容易与 `parse/parsers/registry.py`（不存在）混淆——parser 注册表在 **`openviking/parse/registry.py`**，parser 基类在 `parse/parsers/base_parser.py`。

**一个贯穿全文的观察被 v0.5.0 强化了**：三档开放度里，最开放的是 provider（配置即换），最封闭的是 parser（要 fork）——而这轮 upstream 全部的新增适配器都落在**中间的 ingest source 层**（2 个），provider 层只是 +1 个 adapter。也就是说"离用户数据越近越开放"这条规律，在真实演进里表现为"中间层最先被用起来"。
